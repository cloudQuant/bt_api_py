## 1. 设计目标与原则

### 1.1 目标

把质量治理从"**靠人扫**"改成"**靠门禁挡 + 靠台账推**"：

1. 门禁覆盖全部源码（含 15 个子仓），有明确的**例外清单**；
2. 违规量**单调不增**（棘轮），杜绝"清理一批、新增两批"；
3. 债务**单一台账**可查、可分配、可验收；
4. 修复**分批可回滚**，每批测试全绿。

### 1.2 设计原则

1. **先堵漏再清存量**：没有门禁的清理等于白干（实测一个月 +458 违规即证据）。
2. **棘轮优于阈值**：不设"必须低于 N"的绝对门槛（会一次达标后继续劣化），而是"**不得超过已达成的最好水平**"。
3. **例外显式化**：生成代码（CTP structs）、测试桩（S106）等必须有**书面例外清单 + 理由 + 复核日期**，不允许静默 ignore。
4. **按仓分批**：每个子仓独立提交、独立验证、独立回滚；父仓只 bump 指针。
5. **可复现**：所有指标都能用一条命令重算，避免"文档说 80、CI 管 40"式的失真。

## 3. 核心机制设计

### 3.1 门禁范围扩容（D1 的落地方式）

初始状态是 `lint`/`type-check` 只覆盖核心；当前已保留快速的核心 `lint`，并把完整范围交由
`lint-all` + 阻塞 `quality-ratchet`。这避免日常开发命令因 34 条路径而变慢，同时不允许完整范围的
lint 债回升。

当前实现的范围模型：

```make
# 与 check_quality_ratchet.py 保持一致，含主包、测试、工具、示例和全部子仓 src/tests
QUALITY_SCOPE := bt_api_py tests scripts examples $(SUB_SRC) $(SUB_TESTS)

lint:             ruff check $(CORE_SCOPE)       # 快速开发反馈
lint-all:         ruff check $(QUALITY_SCOPE)    # 全量可见报告
quality-ratchet:  python scripts/ci/check_quality_ratchet.py  # 全量阻塞、只降不升
type-check-l1:    mypy L1 五仓                   # 当前阻塞的子仓类型范围
security-scan:    bandit -r bt_api_py -c pyproject.toml       # 仅主包；子仓安全单列、分阶段准入
```

CI 侧按**分层 job + 矩阵**执行，避免单 job 超时（现状 Quality Gates `timeout-minutes: 15`）：

| job | 范围 | 超时 | 说明 |
|-----|------|------|------|
| `quality-core` | `bt_api_py` + `tests` | 15 min | 保持现有严格度（当前 clean） |
| `submodule-lint` | 矩阵：每个 `bt_api/bt_api_*` 一个分片 | 10 min/分片 | 现为 report-only；10 项 lint 清零、稳定 CI 且可独立回滚后单独转 blocking |
| `submodule-format` | 同上 | 10 min/分片 | 现为 report-only；快照基线 452、当前 dirty checkout 453，须独立清零、稳定 CI 且可独立回滚后单独转 blocking |
| `quality-ratchet` | 全量扫描 + 快照比对 | 10 min | 新增；只判断"是否上升" |

> 当前证据：15 个子仓有 **10** 个 lint 项；`ruff format --check` 的快照基线为 **452**，dirty OKX 使当前总数为 **453**（87 > 86），故 format-ratchet 正确失败。
> 因此已拆开的 `submodule-lint` 与 `submodule-format` 必须仍各自为 report-only；任一维度都不可借另一维度的结果提前升级。
> 取舍：矩阵 jobs 会增加 CI 分钟数，但换来“子仓失败可定位、可并行、可单独豁免”；任何退化都不可失去全量棘轮覆盖。

### 3.2 棘轮（Ratchet）机制

**基线快照格式**（`docs/acceptance/<YYYY-MM-DD>-quality-ratchet.json`）：

```json
{
  "schema_version": 1,
  "generated_at": "2026-09-19T00:00:00+08:00",
  "scope": ["bt_api_py", "tests", "bt_api/*/src"],
  "ruff_version": "ruff 0.16.2",
  "ruff": { "total": 1301, "by_rule": { "W291": 712, "F401": 164, "I001": 154, "F821": 135, "S106": 45, "E701": 36, "F541": 21 } },
  "ruff_exceptions": { "paths": ["bt_api/bt_api_ctp/src/bt_api_ctp/ctp/ctp_structs_*.py"], "reason": "生成代码" },
  "mypy": { "total": 74, "scope": ["bt_api_py"] },
  "coverage": { "bt_api_py": 40.0, "enforced_min": 40 }
}
```

**判定规则**（`scripts/ci/check_quality_ratchet.py`）：

1. 逐规则比较：`current[rule] > baseline[rule]` → **fail**（并打印新增位置的前 N 条）。
2. 规则新增（baseline 无、current 有）→ fail（除非在 `allow_new_rules` 白名单）。
3. 规则清零 → **pass，并提示更新快照**（快照只在下降时更新，单调不增）。
4. scope 在尾部斜杠归一化后必须双向一致：快照记录路径缺失、或当前发现路径未记录，均为 **fail**；普通 `--update` 不得写入这类差异；审查后的 `--force-update` 也只能记录安全扩张，禁止删除既有 scope 或抬高旧范围债务。
5. 例外路径在扫描时排除，但**例外清单本身纳入审查**（新增例外需在本计划或 ADR 中说明理由）。

> 与"绝对阈值门禁"的区别：绝对阈值只保证"不比目标差"，棘轮保证"不比历史最好差"，
> 适合长期劣化型债务（本项目实测一个月 +458，正属此类）。

#### 3.5.2 子仓 format 的独立晋级设计

工作流对每个子仓执行 ruff format --check bt_api/<module>。以同一 Ruff 0.16.2 固化的快照基线为 15 仓共 452 个文件：Binance 100、OKX 86、IB Web 40、Base 33，其余 11 仓合计 193；当前 dirty OKX 为 87，使实时总数为 453。这个计数包含 Ruff 支持的 Markdown 代码块，既是格式债，也可能影响文档示例可读性；它不是 Python 源文件数量。

## 5. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 棘轮过严导致 PR 无法合并 | 高 | 提供**显式例外**通道（台账登记 + ADR），但例外也需记账 |
| 子仓门禁扩容后大量 job 失败、阻塞协作 | 高 | lint 与 format 分成独立 job；每项以零存量、连续 CI 证据和独立 revert 为晋级条件，而非按时间直接翻转 |
| `ruff --fix` 批量改写引入行为变化 | 中 | 仅用安全修复（不带 `--unsafe-fixes`）；按子仓小批提交 + 测试全绿 |
| 子仓 15 个仓库的协调成本 | 中 | 先做 binance/okx（违规集中），其余按批；用 foreach 脚本汇总 |
| 覆盖率提升靠"补空壳测试" | 中 | 强制 `docs/code-quality-baseline.md` 的反空壳判据；高风险模块优先 |
| 文档与门禁再次失真（40 vs 80） | 中 | 覆盖率门槛同源 + 每次变更同步快照 |
| 计划债台账化沦为形式 | 低 | 台账与 CI 棘轮/批次验收挂钩，纳入验收文档 |
