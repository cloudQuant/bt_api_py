## 1. 设计目标与原则

### 1.1 目标

在 `bt_api_ctp` 内实现一套**交易所解耦、可多机分片、高性能、可恢复**的 tick 数据采集与落盘框架，首个实现为 CTP，覆盖国内六大期货交易所（SHFE、DCE、CZCE、CFFEX、INE、GFEX）的全市场期货 + 期权合约深度行情快照。

### 1.2 设计原则

1. **回调轻量化**：CTP 行情回调线程内只做入队/计数，不做 IO、不做重计算，保证不阻塞行情接收。
2. **采集与落盘解耦**：采集线程（或回调）与落盘线程通过内存队列/缓冲隔离，落盘异步进行。
3. **接口交易所无关**：主流程不感知 CTP，通过抽象接口（Protocol）驱动，便于扩展其他交易所。
4. **分片可配置**：分片策略声明式配置，多机各自独立运行，互不依赖。
5. **幂等可恢复**：中断后可重跑，落盘数据带唯一键支持去重。

## 3. 核心接口设计（跨交易所抽象）

> 这是"接口要考虑清楚怎么弄"的关键部分。定义在 `bt_api_ctp`（或提升至 `bt_api_base`）的抽象层，主流程只依赖抽象。

### 3.1 InstrumentProvider（合约提供者）

```python
@dataclass(frozen=True)
class InstrumentSpec:
    instrument_id: str          # 合约代码，如 rb2510
    exchange_id: str            # 交易所，如 SHFE（含 INE，共六家）
    asset_type: str             # "future" | "option" | "combination" | "tas" | ...
                                # 完整枚举对齐 normalize_ctp_instrument 的
                                # ProductClass 映射（future/spot/combination/
                                # efp/spot_option/tas/mi）
    # 期权专属
    underlying_instrument: str | None
    strike_price: float | None
    option_type: str | None     # "call" | "put"

class InstrumentProvider(Protocol):
    def fetch_instruments(self) -> list[InstrumentSpec]:
        """查询当日有效合约全集（含期货+期权）。"""
```

> 实现提示：CTP 实现直接复用现有 `TraderClient.query_instruments_result()`（`bt_api_ctp/ctp/client.py`）+ `normalize_ctp_instrument()`（`bt_api_ctp/instrument.py`），字段归一化已具备。主流程对全集应用类型过滤（默认仅 `future`/`option`，可配置）。

### 3.2 MarketDataSubscriber（行情订阅与回调）

```python
class TickHandler(Protocol):
    def on_tick(self, tick: TickRecord) -> None:
        """收到一条 tick（在行情线程内被调用，须轻量）。"""

class MarketDataSubscriber(Protocol):
    def connect(self) -> None: ...
    def subscribe(self, instruments: list[str]) -> None:   # 支持分批
    def set_handler(self, handler: TickHandler) -> None: ...
    def run(self) -> None:                                  # 阻塞运行，维护重连
    def close(self) -> None: ...
```

### 3.3 TickRecord（归一化 tick 结构）

```python
@dataclass(frozen=True)
class TickRecord:
    exchange_id: str
    instrument_id: str
    trading_day: str           # 交易日（夜盘时段 = 次一交易日，与 action_day 不同）
    action_day: str            # 业务发生日（自然日）
    update_time: str           # 行情时间 HH:MM:SS（原始字符串）
    update_millisec: int       # 行情毫秒（与 update_time 共同构成时间键）
    local_receive_time: int    # 本地接收时间戳(ns，墙钟 UTC epoch)
    # 深度行情字段（对齐 CThostFtdcDepthMarketDataField，逐字段映射不裁剪）
    last_price: float
    volume: int
    turnover: float
    open_interest: float
    open_price: float           # 当日开盘价
    highest_price: float        # 当日最高价
    lowest_price: float         # 当日最低价
    average_price: float        # 当日均价
    bid_price: tuple[float, ...]   # 五档
    bid_volume: tuple[int, ...]
    ask_price: tuple[float, ...]
    ask_volume: tuple[int, ...]
    upper_limit: float
    lower_limit: float
    pre_settlement: float
    pre_close: float
    pre_open_interest: float
    # 其余 CTP 字段以 bt_api_ctp/ctp/ctp_structs_market.py 的
    # CThostFtdcDepthMarketDataField 为准逐一映射（满足 FR-3 / AC-3 "无裁剪"）
```

> 归一化目标是：无论底层是 CTP 还是 Binance，主流程看到的都是 `TickRecord`。
> **毫秒字段是不可省略的时间键组成部分**：CTP 快照 500ms 级推送，同一秒内同合约可有多条快照（部分交易所单窗口推 2 条），去重与排序必须含 `update_millisec`。
> 可选优化：高频路径上避免逐条构造重量级 frozen dataclass——回调线程可仅入队原始 dict，归一化延迟到落盘线程批量执行。

## 4. 关键流程设计

### 4.1 启动 → 订阅流程

```
1. 加载配置（账号、分片、目录、缓冲参数）
2. 判断今日是否为交易日（否则退出）
3. InstrumentProvider.fetch_instruments()  → 全量合约
4. 应用分片策略，过滤出本机负责的合约
5. MarketDataSubscriber.connect() 登录
6. 分批 SubscribeMarketData（每批 N 个，避免超限）
7. 进入 run() 持续接收 tick
```

### 4.2 tick 采集流程（性能关键）

```
行情回调线程 OnRtnDepthMarketData
  → Normalizer.normalize() 轻量转换
  → 写入 per-instrument 环形缓冲（非阻塞，容量有上限）
  → 计数 + 抽样日志

独立落盘线程（异步）：
  定时(如 5s)或缓冲达到阈值
  → 从缓冲批量取出
  → 追加写临时文件/内存 Arrow table
```

> **性能要点**：回调线程绝不直接写盘、绝不加锁重操作；用无锁或轻量锁的环形缓冲；落盘线程独立消费。

### 4.3 收盘清洗流程

```
1. 触发收盘（交易时段结束或手动触发；白盘段与夜盘段各自触发，见第 7 节）
2. 停止订阅，flush 所有缓冲
3. 对每个合约的数据：
   a. 按 (instrument_id, action_day, update_time, update_millisec) 去重，
      同键多条保留 local_receive_time 最新一条（断线重连重订阅可能重推快照）
   b. 按 (update_time, update_millisec) 排序
   c. 字段类型规整 → Arrow schema
4. 写 Parquet：<root>/<trading_day YYYYMMDD>/<exchange>/<instrument_id>.parquet
5. 生成完整性报告 report.json（每合约 tick 数、起止时间、缺口区间，
   缺口含断线时间窗 connection_generation 变化区间）
```

### 4.4 断线重连流程

```
OnFrontDisconnected 回调
  → 标记连接断开，记录断线时间窗（写入当日报告的缺口区间）
  → CTP 原生库自动重连前置；现有 MdClient 在 OnFrontConnected 已内置
    自动重新登录 + 重订阅 _pending_instruments（复用现有实现，不重复造轮子）
  → 恢复落盘；重连后的行情携带新的 connection_generation，
    用于区分重连前后的行情批次与界定缺口
```

> 现状核对：`MdClient`（`bt_api_ctp/ctp/client.py`）的 `_MdSpi.OnFrontConnected` 会自动 `ReqUserLogin`，登录成功后自动重订阅 `_pending_instruments`。采集侧只需：① 把订阅全集保持在 pending 列表；② 跟踪 `connection_generation` 变化记录断线时间窗。

## 5. 数据模型与存储

### 5.1 目录结构

> 目录日期统一采用 **`trading_day`（交易日）**，与 CTP `GetTradingDay()` 一致：夜盘（21:00 起）行情归属**次日** trading_day 目录。例如 20260915（周一）晚 21:00 的夜盘 tick 与 20260916（周二）白盘 tick 都写入 `20260916/` 目录。schema 中同时保留 `trading_day` 与 `action_day` 两个字段以便溯源。

```
<data_root>/
└── 20260916/                     # trading_day YYYYMMDD
    ├── SHFE/
    │   ├── rb2510.parquet
    │   ├── ru2509-C-14000.parquet  # 期权：直接使用 CTP InstrumentID 原样命名
    │   ├── SR509C5000.parquet      # （示例为 CZCE 风格；各交易所格式不同：
    │   └── ...                     #  DCE m2509-C-3000、CFFEX IO2509-C-4000，
    │                               #  但全局唯一且字符均为文件名合法字符）
    ├── DCE/
    ├── CZCE/
    ├── CFFEX/
    ├── INE/
    └── GFEX/
```

### 5.2 Parquet schema

| 字段 | 类型 | 说明 |
|------|------|------|
| trading_day | string | 交易日（夜盘 = 次一交易日） |
| action_day | string | 业务发生日（自然日） |
| update_time | string | 行情时间 HH:MM:SS 原始字符串 |
| update_millisec | int32 | 行情毫秒（排序/去重键组成部分） |
| local_receive_time | int64 | 本地接收时间戳(ns，墙钟 UTC epoch) |
| exchange_id | string | 交易所（SHFE/DCE/CZCE/CFFEX/INE/GFEX） |
| instrument_id | string | 合约代码（同时是文件名） |
| exchange_inst_id | string | 交易所合约代码（`ExchangeInstID`） |
| last_price | double | 最新价 |
| volume | int64 | 成交量（当日累计） |
| turnover | double | 成交额 |
| open_interest | double | 持仓量 |
| open_price / highest_price / lowest_price | double | 当日开/高/低 |
| average_price | double | 当日均价 |
| bid_price_1..5 | double | 买一~五价 |
| bid_volume_1..5 | int64 | 买一~五量 |
| ask_price_1..5 | double | 卖一~五价 |
| ask_volume_1..5 | int64 | 卖一~五量 |
| upper_limit / lower_limit | double | 涨跌停 |
| pre_settlement / pre_close | double | 昨结/昨收 |
| pre_open_interest | double | 昨持仓 |
| （其余字段） | — | 以 `CThostFtdcDepthMarketDataField` 全字段清单为准，逐字段映射不裁剪 |

> 排序键与去重键：`(action_day, update_time, update_millisec)`；同一键多条时保留 `local_receive_time` 最新一条。

### 5.3 缓冲设计

- 采用 **per-instrument 的 AppendBuffer**（可用 `collections.deque` 或 Arrow RecordBatch 追加）。
- 单合约缓冲上限可配（如 10 万条），达到上限后策略可配：**丢弃并告警** 或 **强制刷盘**。
- 全局内存预算可配，超出时优先刷盘最活跃合约。

### 5.4 中断恢复与合并写

- 当日进程中断后重跑 `--once`：sink 先读取该合约当日已有 parquet，与新采集数据合并去重后**原子替换**写回（临时文件 + rename），保证幂等。
- CTP 行情不可回放历史，**往日数据无法补采**；跨日缺口只能通过后续迭代的合并/外部数据源方案弥补，不在本期范围。

## 6. 分片设计

### 6.1 分片策略

| 策略 | 说明 | 适用 |
|------|------|------|
| 按交易所分片 | 每台机器负责一个或多个交易所 | 机器少、交易所边界清晰（推荐） |
| 按品种前缀分片 | 如 rb/cu/au 归机器 A，期权按标的归机器 B | 更细粒度 |
| 哈希取模分片 | `hash(instrument_id) % N == shard_id` | 均匀负载，但冷热不均 |

### 6.2 配置示例

```yaml
# collector.yaml
data_root: /data/tick
shard:
  strategy: by_exchange
  exchanges: [SHFE, DCE]          # 本机负责
# 或 hash:
# shard:
#   strategy: hash_mod
#   shard_id: 0
#   total_shards: 3
buffer:
  per_instrument_cap: 100000
  flush_interval_sec: 5
schedule:
  pre_open_minutes: 10            # 开盘前 N 分钟启动（白盘 ~08:45 / 夜盘 ~20:45 两段）
  night_session: auto             # 夜盘段是否运行：auto=按交易日历与订阅品种判断
  close_times:                    # 各段收盘清洗触发时间（按分片内最晚品种配置）
    day: "15:16"
    night: "02:31"
  auto_close: true                # 收盘自动清洗
ctp:
  env: simnow                     # 或 production
  # 账号等沿用 ctp_env_selector 配置
```

## 7. 调度设计

- **手动模式**：`python -m bt_api_ctp.collector --config collector.yaml --once`，用于开发、调试、当日中断后的恢复。
- **自动模式**：
  - Linux 服务器：`systemd timer` 或 `cron` 触发。
  - macOS 本地：`launchd` 或脚本内置等待循环。
- **交易时段与两段式运行**：一个交易日 = 夜盘（**交易日的前一晚** 21:00 起，最晚品种至次日 02:30）+ 白盘（09:00–15:15，含小节休息）。**夜盘归属**：**周五晚的夜盘 + 周一的日盘 = 一个完整交易日**，周日晚无夜盘，法定节假日前一交易日晚夜盘暂停。由此调度时点为——**交易日当晚 ~20:45**（夜盘段，周一~周五）与**交易日当天 ~08:45**（白盘段），由外部调度器分别触发（`--night` 区分），或采用常驻进程跨段管理。落盘目录沿用 CTP `TradingDay`，周五晚数据自然归入下周一目录。
- **时段与收盘口径**：白盘组 = 09:00-10:15 / 10:30-11:30 / 13:00-15:15（含小节休息），夜盘组 = 21:00-02:30。`--until-close` 跑到**本组最后一个小节的结束**（10:00 启动也跑到 15:15），`--wait-open` 支持 08:45/20:45 提前启动后等待开盘。
- **交易日历**：本地维护国内期货交易日历（节假日表或第三方库）用于启动预判与夜盘有无判断；登录后以 CTP `GetTradingDay()` 为**权威交易日**，目录与数据中的 `trading_day` 以此为准。
- **收盘触发**：按交易时段两段触发——白盘收盘后（如 15:16 起，可配；注意中金所部分品种 15:15 才收盘）触发白盘段清洗；夜盘按分片内订阅品种的最晚收盘档（23:01 / 01:01 / 02:31，可配）触发夜盘段清洗。两段清洗合并写入同一 `trading_day` 目录。

```
│   └── normalizer.py             # OnRtnDepthMarketData → TickRecord
```

> 说明：抽象接口是否上提至 `bt_api_base` 需在实现阶段评审——若未来 Binance/OKX 也在各自插件内复用同一套主流程，则抽象层与 `engine.py`/`buffer.py`/`sink.py` 上提至 `bt_api_base` 更合理。本设计文档暂将主流程放 `bt_api_ctp`，并明确"可上提"的演进路径。

## 9. 性能设计细节

| 关注点 | 设计 |
|--------|------|
| 回调不阻塞 | `OnRtnDepthMarketData` 内仅归一化 + 无锁入队 |
| 无锁/轻量缓冲 | per-instrument deque 或分段环形缓冲，避免全局锁竞争 |
| 归一化开销 | 高频路径避免逐条构造重量级 frozen dataclass：回调线程仅入队原始 dict（或用 `slots`/对象池），归一化延迟到落盘线程批量执行 |
| 批量落盘 | 定时 flush，Arrow 批量写 Parquet，避免逐条 IO |
| 订阅分批 | 每批订阅 N 个（N 需实测，初设 100），批次间短间隔 |
| 内存保护 | 单合约/全局缓冲上限，超限告警或强制刷盘 |
| 主进程模型 | 可选：回调线程 + 单落盘线程；或 asyncio 事件循环 + 队列 |
| 编译产物复用 | 直接复用现有 `ctp_md_api` 的 C++ 扩展，不重复编译 |

## 10. 可靠性与可观测性

### 10.1 可靠性

- 断线自动重连 + 重新订阅（复用 `MdClient` 内置的自动重登+重订阅，见 4.4）。
- 幂等落盘：去重键 `(instrument_id, action_day, update_time, update_millisec)`，重跑不产生重复。
- 当日恢复：进程中断后 `--once` 重跑，与当日已落盘数据合并去重（见 5.4）；CTP 行情不可回放，往日数据无法补采。

### 10.2 可观测性

- 结构化日志：连接状态、订阅成功/失败数、每合约 tick 计数、flush 耗时、内存占用。
  每合约 tick 计数由 `TickCollectionEngine._report_tick_milestones` 输出，模式 `every`（每累计到 `tick_interval` 整数倍报一次**累计值**）；`first`（仅首次达标）变体**已删除**，见《整改方案.md》D16。
- 收盘报告：`report.json` 记录每合约 tick 数、起止时间、缺口区间。
- 可选指标导出：prometheus 指标（复用现有 monitoring 能力，可选）。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| CTP 订阅数量限制 | 高 | 实测上限，分批订阅 + 间隔；必要时多行情账号 |
| SimNow 订阅数量/权限限制 | 中 | SimNow 仅用于小规模开发验证；全市场压测与生产采集使用生产账号 |
| 期权合约数量庞大导致单机内存/带宽不足 | 高 | 分片刚性要求 + 缓冲上限 + 冷热分流 |
| 行情高峰丢 tick | 高 | 回调轻量化 + 无锁缓冲 + 落盘线程独立 |
| 不同交易所 tick 频率差异大 | 中 | 缓冲策略可配，冷门合约降频处理 |
| 夜盘跨零点 / 节前无夜盘的调度错误 | 中 | trading_day 权威口径 + 交易日历预判 + 两段式调度（见第 7 节） |
| 生产环境权限/账号 | 中 | SimNow 先行验证，生产前确认行情权限 |
| C++ 扩展跨平台 | 中 | 复用现有编译产物，CI 三平台验证 |

## 13. 接入新交易所（Binance / OKX 等）的步骤

1. 新建采集实现包（如 `bt_api_binance/collector_binance/`），实现三个协议：
   - `InstrumentProvider.fetch_instruments()` → `list[InstrumentSpec]`
   - `TickNormalizer.normalize(raw)` → `TickRecord | None`
   - `MarketDataSubscriber`（`connect` / `subscribe` / `set_handler` / `run` / `close`），内部组合该交易所的 normalizer，保证 `handler.on_tick()` 收到的是 `TickRecord`
2. **复用主流程**：直接使用 `bt_api_ctp.collector` 的 `TickCollectionEngine` / `TickBuffer` / `ParquetSink` / `ShardConfig` / `TradingCalendar`——它们不依赖 CTP（`collector` 包内不得出现交易所专属 import，已有测试断言这一点）。
3. **落盘零改动**：`ParquetSink` 的路径与 schema 与交易所无关，不同交易所按 `exchange_id` 分目录。
4. 适配点检查：
   - 新交易所若无"交易日 / 夜盘"概念，可替换或跳过 `TradingCalendar`；
   - tick 频率显著高于 CTP 时，调大 `per_instrument_cap` 或改用 `overflow_policy: flush`；
   - 按其吞吐调整 `flush_interval_sec` 与订阅 `batch_size`。
5. **验收方式**：仿照 `tests/collector/test_integration_fake_exchange.py`，用假实现跑通 `run_once` 并落盘，证明主流程未被改动。
