## 3. 发现的问题与改进建议

### P1 订阅 ACK 就绪判定：15s 定值窗口对全市场规模必然误报（高）

- 现象：`subscribe acknowledged: requested=17002 acked=1134 failed=0 timed_out=15868` + WARNING
  "subscribe not ready"；但心跳显示 `sub_ok=34004`（=17002×2，含重订阅）——**柜台 ACK 最终全部到达**，
  数据也从 21:04:45 起正常流入。
- 根因：`collector/engine.py` `_await_subscription_ack(..., timeout_sec=15.0)` 是定值窗口，只等待一次判
  定；SimNow 对万级订阅的 ACK 是缓慢分批回放的（15s 内仅 6.7%）。
- 建议：① 窗口改为**滚动观察**：ACK 持续计数，直到 `acked==requested` 或"实际行情到达数≥阈值"才判就绪；
  ② 就绪前的 WARNING 措辞降级为 INFO+计数，超过 `subscription_ready_timeout_sec`（建议 120s 可配）仍
  无数据才 ERROR；③ report 增加 `ack_final` 快照，便于事后核对。

### P2 健康告警风暴：19 条 ERROR 全为误报，两个校准缺陷（高）

- 现象：21:13–21:23 每分钟一条 `collection health alarm: 16xxx/17002 recently active instruments silent
  for more than 300s`；02:27–02:28 收盘前再次连发。
- 根因 A（开盘风暴）：订阅时 CTP 推送的**合成快照**被 `collector/health.py` 的 `observe()` 计入
  "近期活跃"（17002 全量），21:04 首帧后 5 分钟集体"静默"→ 风暴。而 sink 的 `_outside_session()`
  已把这 11294 条合成快照正确挡在落盘外——**health 与 sink 的观察口径不一致**。
- 根因 B（收盘风暴）：沉默分母没有按交易所时段剔除：02:27 时 CZCE/DCE（23:00 收）、GFEX/CFFEX
  （**均无夜盘，整晚静默属预期**）仍在 17002 分母里，`silent_share>0.8` 恒真。
- 建议：① health 只统计通过 `_outside_session`（或"本交易时段+真实时间戳"）过滤后的 tick，与 sink 共用
  分类器；② 分母改为"**该交易所当前处于交易时段内的活跃合约**"——需要内置按交易所的时段表
  （**CFFEX、GFEX 无夜盘，日盘 only**；DCE/CZCE 夜盘至 23:00；SHFE/INE 分档 23:00/01:00/02:30），
  同一张表也解决 P3 的判据来源。

### P3 交易所夜盘可用表缺失：本轮误判的根源（中，可观测性；v1.1 订正）

- **事实订正**：v1.0 把"连续两晚夜盘 GFEX 3890 合约全部 0 tick"判为"SimNow 第一套备用前置不转发 GFEX
  夜盘行情"，并要求生产复核——**该判断错误：广期所（工业硅 si、碳酸锂 lc、多晶硅 ps 及其期权）不开放夜盘**，
  与中金所（CFFEX）同为日盘-only 交易所。两晚 GFEX/CFFEX 夜盘零数据均为**正常市场行为，不构成任何异常**；
  9/17 日盘 GFEX 3890/3890 合约有数据（26944 行至 15:02）本就证明采集链路正常。
- 遗留的真实缺口：系统与人都缺少"按交易所的夜盘可用性"概念，无法区分**预期静默**（CFFEX/GFEX 夜盘）与
  **异常静默**（应有夜盘的交易所整所无数据）——第一晚把正常的零数据误读成"22:30 停更"、v1.0 写出
  "环境不覆盖"，都是这张表缺失的直接代价。
- 建议：① 时段表增加各所夜盘可用性标注（**CFFEX、GFEX：无夜盘**；DCE、CZCE：21:00–23:00；SHFE、INE：
  品种分档 23:00/01:00/02:30），"夜盘开局 5–10 分钟整所 tick==0 → ERROR"的告警只对**应有夜盘**的交易所生效；
  ② report 顶层增加 per-exchange 的 `subscribed/received/zero_data` 三计数并按 ① 标注 `expected: yes/no`
  ——现在 20260918 里 GFEX/CFFEX 目录整体缺失是隐式信息，"正常零"与"异常零"在报告里不可分辨；
  ③ 把"各所交易时段矩阵（含品种分档收盘时间）"作为静态配置归档到本目录，以交易所公告为准维护，
  作为调度、health 告警、报告的共同事实来源，杜绝运行时再猜。

### P4 `expected_ticks/coverage/estimated_missing` 对低流动性合约为系统性虚警（中）

- 现象：全所 mean coverage 仅 0.006–0.033，`estimated_missing_ticks` 合计 125 万；CF709（棉花旧月）
  coverage=0.0001。而真实断线窗只有 81 秒。
- 根因：`expected_ticks` 以"500ms×2 全程连推"为基线，但 CTP 仅在**盘口有变化**时推送，冷门合约/期权
  几分钟一条是市场常态，不是采集缺口。125 万"缺失"几乎全是噪声，淹没真实信号。
- 建议：① 该组指标只对"活跃合约集"（本时段收到 ≥N 条）计算，冷门合约只报 rows/起止；② 缺失推断改用
  已实现的 `volume_jumps` + **同所横向关联**：同一分钟窗口内该所多数活跃合约 volume 跳变→判采集断，
  仅个别合约跳→判行情静默；③ report 文档化该字段语义，避免下游误读。

### P5 存量数据污染：20260917 目录每合约 1 行幽灵快照（中，一次性清理）

- 现象：9/16 晚旧版运行时，20:18:42.726 的订阅合成快照（`action_day=20260916`、`trading_day=20260917`、
  无盘口 bid1=None）作为唯一行写入了全部 16956 合约文件，并污染 report 的 `first_update`。
- 现状：工作区新版 sink `_outside_session()` 已阻止此类行再入库（今晚 `ticks_outside_session=11294` 全部
  被拦截），**增量已修复**。
- 建议：对 `tick_data/20260917/` 跑一次性清洗（删除 `update_time=20:18:42` 且 `bid_price1` 全空的行）
  或重新生成该日报告；并在数据使用文档注明该日的已知污染特征。同时清理 0 字节残留
  `tick_data/logs/collector-20260916.log`（旧版日志命名缺陷的遗迹，现版本按交易日命名已正确）。

### P6 版本漂移：验收对象不在任何已固化提交里（中，流程）

- 现象：今晚运行的是工作区未提交代码（health.py、staging compaction、`_outside_session` 均只在工作区）；
  anaconda site-packages 是 9/17 14:05 安装版（engine 无 health）；9/17 早间日盘用的恰是旧 site-packages 版。
  **同一迭代的两晚运行并非同一份代码**，report 字段也因此不一致（20260917 无顶层诊断字段、20260918 有）。
- 建议：① 把工作区改动提交为独立 commit（如 `feat(collector): session-health guard + outside-session filter`），
  重装到运行环境；② 验收记录一律绑定 commit hash 与 `pip show bt_api_ctp` 版本；③ deploy 脚本固定
  解释器与安装来源（systemd unit 里写绝对路径 venv，避免 site-packages/worktree 混用）。

### P7 内存与吞吐留痕（低）

- PF-3 内存上限目前只能靠 `per_instrument_cap` 间接保证。建议 heartbeat 行追加 `rss_mb` 与
  buffer 水位最高值，使"整夜不 OOM"成为可核查证据；收盘 report 附 max_rss。

### P8 SimNow 凌晨例行断开的预期化（低）

- 02:12 左右前置重启是 SimNow 第一套的规律行为（本轮 reason=4097）。建议在 `disconnects` 诊断里
  自动标注"距收盘 <20 分钟的断开"并给出预期提示，避免与故障断开混淆。
