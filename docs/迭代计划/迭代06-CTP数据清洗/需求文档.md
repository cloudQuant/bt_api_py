## 1. 背景与目标

### 1.1 背景

迭代04（CTP 全市场 tick 数据采集与落盘）已完成 M1–M5：多机分片采集、按
`<data_root>/<trading_day>/<交易所>/<合约>.parquet` 落盘、收盘清洗去重、
完整性报告（`report.json`）。当前状态：

- 本地笔记本与多台远程服务器**各自持有自己分片**的 tick 数据，迭代04 明确
  "跨机自动汇总/去重留待后续迭代"，现在多机数据分散、无法集中消费。
- 落盘数据自带去重键 `(instrument_id, action_day, update_time, update_millisec)`
  且 `merge_existing` 支持当日重跑合并，但仅限**单机当日**；跨机器、跨日的
  集中合并尚无工具。
- 研究侧主要消费形态是 K 线（1/5/15 分钟），tick→K 线的合成能力缺失
  （现有 `data_downloader.py` 只覆盖 K 线下载，不含本地 tick 合成）。

本迭代补齐"**拉取 → 校验 → 合并 → 安全回收 → K 线合成**"的每日清洗链路。

### 1.2 目标

1. **数据集中**：每日定时从多台远程服务器拉取已落盘的 tick 数据到本地。
2. **去重合并**：远程与本地数据按交易所组织，按迭代04 同款去重键合并去重、
   按行情时间排序，**合并写回本地 `ctp_data` 原目录**——本地成为唯一权威 tick 库。
3. **安全回收**：仅当某目录"拉取校验通过且合并完成"后才删除远程对应数据；
   没拉取过、校验不过，远程数据**绝不删除**。
4. **K 线合成**：对清洗后的 tick 合成 1 分钟、5 分钟、15 分钟 K 线。
5. **K 线存储规范**：`<kline_root>/<交易所>/<品种>/<合约>_{1min,5min,15min}.parquet`，
   不按日期分目录，单文件跨日追加。

### 1.3 非目标（本期明确不做）

- 不修改迭代04 采集侧的任何代码（`collector/`、`collector_ctp/` 只读复用）。
- 不做实时/盘中同步（每日一次批量，盘后运行）。
- 不合成日线及以上周期（后续按需扩展）。
- 不在远程服务器上安装 Python 或本项目代码（仅使用 ssh / rsync / sftp
  标准通道；Windows 侧只需内置 OpenSSH Server 的 SFTP）。
- 不做 tick 数据修复（异常/损坏文件仅隔离并列入报告，不尝试修补）。
- 不做 K 线复权、换月主力连续合约等研究侧加工（属回测/数据服务范畴）。

## 2. 用户故事与场景

### US-1 数据集中（核心用户）

> 作为量化研究员，我希望每天收盘后，各台服务器采集的 tick 数据自动集中到
> 我的笔记本上，按交易所合并去重、按时间排序，这样我只用读一个目录就拿到
> 全市场数据。

### US-2 安全删除（运维者）

> 作为运维者，我希望脚本只有在**确认拉取成功并合并完成后**才清理远程服务器
> 上已拉取的数据；只要没拉取或校验没通过，远程数据必须原样保留，防止任何
> 情况下丢数据。

### US-3 定时自动（运维者）

> 作为运维者，我希望每个交易日下午 4 点自动运行整个流程（拉取→合并→删除→
> K 线），无需手动干预；节假日自动跳过。

### US-4 K 线合成（核心用户）

> 作为量化研究员，我希望清洗完的 tick 数据自动合成 1 分钟、5 分钟、15 分钟
> K 线，包含开高低收、成交量、成交额、持仓量，能直接被回测框架读取。

### US-5 K 线路径规范（数据使用者）

> 作为数据使用者，我希望 K 线文件路径稳定可预期：`交易所/品种/合约_{周期}`，
> 同一合约一个周期只有一个文件，跨日自动追加，不要按日期散落成每日一个目录。

## 3. 功能需求

### FR-1 远程数据拉取

- 支持配置**多台**远程服务器；环境为 **Linux + Windows 混合**：
  - Linux 走 `rsync` over SSH（增量传输，天然幂等续传）；
  - Windows 走 `SFTP`（OpenSSH 内置，无需额外安装）；
  - 传输后端抽象（`PullBackend`），每台机器在配置中声明 `backend` 类型与连接参数。
- 拉取对象：远程 `<remote_data_root>/<trading_day>/` 下与迭代04 一致的落盘内容
  （各交易所目录的 `*.parquet` + `report.json`）；**排除**运行时文件
  （`*.lock`、staging 段文件/临时目录）。
- **完成信号**：仅拉取远程已生成 `report.json` 的 trading_day 目录
  （= 远程当日采集已收盘清洗完成）；未完成的目录本轮跳过、不删除，留待下次。
- 拉取落地到本地 **staging 区**（不直接写权威库）。
- **补拉积压**：扫描远程所有"已完成且未删除"的目录（不限于当天），
  本地停机/节假日造成的积压在下次运行时自动补齐。
- 幂等：重复运行不产生重复数据（rsync 增量；SFTP 按远端字节数跳过已完整传输的文件）。

### FR-2 拉取校验

- 校验内容（三级）：
  1. **文件清单一致**：staging 内 parquet 文件 + `report.json` 与远程清单完全一致；
  2. **字节数一致**：逐文件 size 与远程 `list` 结果一致；
  3. **本地可读**：staging 内每个 parquet 可打开、行数可读（记录入 manifest）。
- 校验结果写入 **manifest**（拉取状态档案，含状态机：
  `discovered → pulled → verified → merged → deleted`，失败态 `failed`）。
- 校验失败：保留 staging 与远程数据，输出告警清单，该目录**不进入**合并与删除环节。

### FR-3 去重合并

- 合并输入：staging 中各机器数据 + 本地权威库（`ctp_data`）现有数据。
- 按交易所目录组织；逐合约文件合并：
  - 去重键沿用迭代04：`(instrument_id, action_day, update_time, update_millisec)`，
    同键多条保留 `local_receive_time` 最新一条（多机重叠采集、断线重推均覆盖）；
  - 按 `(action_day, update_time, update_millisec)` 升序排序；
  - 合并结果**原子写回本地权威库原路径**（临时文件 + rename，复用迭代04 原语）。
- 合并统计：每合约"新增行数 / 去重行数 / 合并后总行数"，写入当日清洗报告。

### FR-4 远程删除（安全回收）

- 删除前置条件（**全部满足**才允许执行）：
  1. 该 trading_day 目录在 manifest 中状态为 `merged`（校验通过且合并完成）；
  2. 删除动作在配置中开启（`delete_remote_after_verify: true`，默认 true）；
  3. 远程目标路径通过白名单校验：位于该机器 `remote_data_root` 之下，且目录名
     为合法 `YYYYMMDD` 交易日格式。
- 删除粒度：按远程 trading_day 目录**整体删除**（含残留 lock/staging 运行时文件）。
- 任何一级校验失败或合并失败 → 远程数据原样保留，仅报告告警。
- 支持 `--dry-run`：打印将删除的远程路径清单而不实际执行。

### FR-5 K 线合成

- 输入：本地权威库（`ctp_data`）的 tick parquet；输出：1 分钟、5 分钟、15 分钟 K 线。
- 聚合方式：1 分钟从 tick 直接聚合；5/15 分钟从 1 分钟聚合（保证多周期间口径一致）。
- K 线字段：
  - `datetime`：桶起始时间（`action_day + update_time + update_millisec` 构造，交易所本地时间，钟面对齐）；
  - `open / high / low / close`：桶内 `last_price` 首/最高/最低/末（无效价——非正、inf——的 tick 行不参与 OHLC）；
  - `volume` / `amount`：CTP 当日累计 `volume` / `turnover` 的**桶间差分**
    （负值即跨日重置时改用桶内末−首，仍为负钳为 0 并告警）；
  - `open_interest`：桶内末条持仓量；
  - `trading_day`、`instrument_id`、`exchange_id` 保留。
- **覆盖期货 + 期权**：品种归属由六所命名规则表（`cleaner_ctp/symbols.py`）识别；
  无法识别的合约进入告警清单并跳过，不阻塞其他合约。
- 非交易时段（小节休息、午休）无 tick 自然无桶，不造空桶。
- **跨日追加**：新 K 线与已有 K 线文件按 `datetime` 桶键合并去重（新桶覆盖旧桶）、
  排序后原子替换写回。
- **历史回填**：`--backfill [--since YYYYMMDD]` 对本地已有的全部（或指定范围）
  tick 数据按日顺序合成，首次部署时一次跑通。

### FR-6 K 线存储规范

- 路径：`<kline_root>/<交易所>/<品种>/<合约>_{1min,5min,15min}.parquet`。
- **不按日期分目录**；同一合约同一周期只有一个文件，跨日追加。
- 品种目录名用标的品种代码原样（如 SHFE `rb`、CZCE `SR`、CFFEX `IO`）；
  期权归入其标的品种目录（如 `m2509-C-3000` → `DCE/m/`）。
- `kline_root` 可配置，默认 `<tick_root>/kline`。

### FR-7 定时调度

- 每个交易日 **16:00** 运行（初始需求"每个工作日 4 点"结合"收盘后拉取当日数据"
  的语义定为下午 16:00）：
  - 调度器按周一~周五 16:00 触发（cron / launchd，示例随 `deploy/cleaner/` 提供）；
  - 脚本内置交易日判断（复用迭代04 交易日历与节假日文件机制），
    非交易日以退出码 3 直接退出。
- 16:00 的依据：trading_day T 的数据 = T−1 晚夜盘 + T 白盘（15:15 收盘 +
  close-grace 300s + 收盘清洗落盘），16:00 时 T 目录已完整（`report.json` 已生成）；
  当晚 21:00 起的夜盘写入 T+1 目录，与本轮拉取/删除无冲突。
- 支持手动触发单阶段命令（`pull` / `merge` / `kline`）与 `--dry-run`。

### FR-8 每日清洗报告

- 每次运行生成 JSON 报告：`<tick_root>/cleaner/reports/clean-<trading_day>.json`。
- 内容：各机器各目录的拉取/校验/删除状态、合并统计（合约数、新增/去重行数）、
  K 线统计（品种数、合约数、各周期新增行数）、异常清单
  （校验失败、品种识别失败、隔离文件）。
- 退出码语义与迭代04 对齐：0 成功；1 配置错误；2 连接/传输失败；3 非交易日；
  4 合并/合成失败（含部分失败）。

## 4. 非功能需求（NFR）

### NFR-1 安全性（重点）

- 远程删除三重保护：校验通过（verified→merged）+ manifest 留痕 + 路径白名单。
- 全流程幂等：任意阶段中断后重跑无副作用（staging 残留可复用或清理重来、
  合并可重入、K 线追加可重入）。
- 所有权威库写入均为原子替换（临时文件 + rename），与迭代04 同款。
- 进程互斥：cleaner 运行期间持锁，防止手工触发与定时调度重叠执行。

### NFR-2 性能

- 单日全市场量级（数千 parquet 文件、数千万行 tick）：拉取受网络支配不设硬指标；
  **合并 + K 线合成本地处理目标 ≤ 30 分钟**（16:00 启动、17:00 前完成；实测校准）。
- 逐合约文件流式处理，峰值内存与"单合约最大文件"同量级，不随全市场总量线性增长。
- 拉取前做本地磁盘空间预检（远程清单字节数 × 1.2 与可用空间比较），不足则告警退出。

### NFR-3 可移植性

- 主脚本在本地 macOS 运行（也可在任何装有 Python 3.10+ 的机器运行）。
- 不要求远程安装任何额外软件：Linux 需 `rsync`（发行版标配）；Windows 需启用
  OpenSSH Server（SFTP，系统可选功能）。
- 配置文件沿用迭代04 惯例：相对路径、跨机器可复用、敏感信息走 `.env`。

### NFR-4 可观测性

- 结构化日志：每机器/每目录/每阶段（列出清单、字节数、耗时、结果）。
- 每日清洗报告（FR-8）+ manifest 全量留痕。
- 告警显式列出机器名与文件名（校验失败、删除失败、品种识别失败、隔离文件）。

### NFR-5 数据质量

- 本地权威库 tick schema 与迭代04 **完全一致**（cleaner 不改 schema、不裁剪字段）。
- K 线 schema 固定且与交易所无关（见研发设计文档），多周期间自洽
  （5/15 分钟由 1 分钟聚合，可相互验证）。

## 5. 约束与假设

### 5.1 约束

1. 远程服务器 Linux + Windows 混合；Windows 无原生 rsync，传输后端必须双实现。
2. 16:00 定时依赖本地电脑开机联网；未开机则当日漏拉，依赖 FR-1 的补拉机制
   在下次运行时补齐（远程数据在被删除前始终保留）。
3. 期权命名依赖各交易所现行规范（DCE/GFEX `m2509-C-3000`、CZCE `SR509C5000`、
   SHFE/INE `rb2510C3200`、CFFEX `IO2509-C-4000`）；规则变化需更新规则表。
4. SFTP 通道下海量小文件的遍历/传输性能有限（单日数千文件），需分批与并发控制，
   首次部署实测校准。
5. staging 与权威库并存期间磁盘占用约翻倍，空间预检必须先行。

### 5.2 假设

1. 各机器 data_root 均遵循迭代04 目录规范（`<trading_day>/<交易所>/<合约>.parquet`
   + `report.json`）。
2. 远程 collector 正常完成当日清洗（生成 `report.json`）；未完成的异常目录
   属于迭代04 运维范畴，cleaner 只跳过、不删除。
3. 本地磁盘可容纳全市场集中数据（含 staging 瞬时双份）。
4. 远程服务器在 16:00 前后可SSH/SFTP 访问（无需跳板/VPN 特殊链路；如后续有，
   连接参数在配置中扩展）。
