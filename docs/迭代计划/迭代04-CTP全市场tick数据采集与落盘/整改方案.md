迭代04 的代码链路（合约查询 → 分批订阅 → 缓冲 → Parquet 落盘 → 清洗 → 报告）已在离线契约测试与首轮真实连通行验证中通过。但 2026-09-17 用 `--until-close` 跑完一个完整交易日（白盘段）后，对落盘数据做了完整性核验，结论与验收文档的"通过"不一致：

**链路是对的，数据内容不可用。**

本方案记录核验证据、根因判断与整改任务清单，作为下一轮修复的输入。

**(e) 失败机理（由时间戳还原）**

以 `CZCE/AP701` 为例：09:13–09:29 密集推送 → 09:29–14:23 几乎全静默 → 14:23–15:00 又密集推送。
所有合约在 `09:56:47`、`10:15:00`、`10:30:00`、`10:33:50`、`13:30:00`、`13:43:2x`、`14:16:2x`、`14:53/14:56/14:57` 这些时刻**同时只收到 1 条快照**，与 3.1(b) 的重订阅波次逐一吻合。可还原为三步：

1. 每轮订阅波，前置对每个合约只推 1 条初始快照；
2. 前置只对有限活跃子集持续推送，子集随时间/重订阅轮换；
3. 重连 → 单次全量重订阅 → 再次触发 1、2，形成正反馈（订阅风暴 → 心跳超时断线 → 再风暴）。

## 4. 根因分析

### 4.1 主因（待实验确认）

**SimNow 前置无法承载单连接 1.7 万合约订阅。** 支撑：

- 订阅 ACK 处理速率仅约 27 个/秒（16,956 个订阅耗时 10.5 分钟），后续每轮全量重订阅又需要 10~15 分钟；
- 白盘 12 次断线原因码均为"接收心跳超时"，指向前置侧过载而非本地网络；
- 数据只对有限子集持续推送，且子集在重订阅后轮换；
- CFFEX（720 个合约）基本可用，商品六所（16k+）几乎不可用，与"每连接承载量"假设一致。

需求文档 5.1 与验收文档 10.4 已提示"SimNow 对订阅数量另有额外限制，全市场规模压测需生产账号"，本轮数据与该提示一致。

### 4.2 框架放大因素

| 放大点 | 说明 |
|--------|------|
| 重连后单次全量重订阅 | 每次重连都把 16,956 个订阅塞进一次原生调用，加重前置负担，形成重连风暴 |
| 落盘读写放大 | "每 5s 读旧文件 + 去重 + 整文件重写"使 IO 呈二次方增长，单次 flush 阻塞主循环数分钟 |
| 断线不可观测 | 断线无日志、无回调、代次变化不进报告，问题只能靠事后挖数据才发现 |
| 无健康守卫 | 已订阅但 0 推送时既不告警也不重试，进程"看起来正常" |
| 订阅 ACK 语义误用 | `sub_failed=0` 只表示前置 ACK 无错误码，不代表数据在推；日志"subscribe acknowledged: ok=N"缺"请求数/超时"上下文 |

## 6. 连接与会话容量（分片前置约束）

> 本节依据 CTP 6.7.11 官方文档《报单流控、查询流控和会话数控制》，用于回答"一台机器能连几个 / 单机多连接是否可行"。

### 6.1 CTP 的四类相关限制

**限制不在"机器"，而在"账号 + 前置"。**

| 编号 | 限制 | 配置位置 | 超限表现 |
|------|------|---------|---------|
| 4 | **前置连接数流控 `ConnectFreq`**：同一 IP 每秒允许的最大 API 连接请求数（`init` → `OnFrontConnected` 算一次，与登录无关） | 交易前置组件 | 被**主动断开**并触发 `OnFrontDisconnected`；可用 `whiteiplist` 加白 |
| 5 | **同一用户最大允许在线会话数**：同一 `UserID` 在本交易系统同时在线的会话上限（针对整个系统，**不是单一前置**） | 柜台 / 交易核心（6.6.3+ 支持按用户配置） | `OnRspUserLogin` 返回 `CTP:用户在线会话超出上限` |
| 2 | 查询流控 `QryFreq` + API 内置"在途查询流控 1 笔" | 交易前置组件 | `OnRspError`：`CTP：查询未就绪，请稍后重试` / 返回 -2 |
| 3 | FTD 报文流控 `FTDMaxCommFlux`：登录、查询、报单等全部请求均计入 | 交易前置组件 | 无报错，请求被前置缓存到下一秒（表现为延迟） |

因此：**单机连接数上限 = 账号维度的第 5 条 × 前置维度的第 4 条 × 交易所行情系统的账号级订阅配额。** 第 5 条的取值由柜台配置决定，本文档无法给出，必须向券商 / SimNow 确认（见 6.5）。

### 6.2 与本轮断线的关联

第 4 条 `ConnectFreq` 按"同 IP 每秒建连数"限流，超限直接踢连接。本轮的失败路径恰好会踩中它：

```
断线 → CTP 原生自动重连 → OnFrontConnected → 登录 →
单次全量重订阅 16,956 个合约 → 前置过载 → 心跳超时断线 → 循环
```

即第 3.1 节的 12 次断线中，至少一部分可能是"被前置主动踢"而非纯网络故障。在 D1 / P1-3 修复前，单纯增加连接数会加重该循环。重连后重订阅的分批要求，以及"不得阻塞 CTP 回调线程"的约束，见第 7 节「重连重订阅契约」。

### 6.3 单机多连接：可行，但有 4 个代码坑

多账号 / 多连接分摊订阅、主备冗余是行业标准做法。本仓代码需要先解决：

| # | 坑 | 位置 | 说明 / 处置方向 |
|---|----|------|----------------|
| 1 | 同账号多实例共用 flow 目录 | [client.py:792](../../../bt_api/bt_api_ctp/src/bt_api_ctp/ctp/client.py:792) | `_flow_dir` 只按 `md_{broker}_{user}` 哈希；同账号两个 MD 连接会写同一份 `.con`，需改为"每连接唯一 flow 目录" |
| 2 | 每进程独立登录 TD 查询合约 | [cli.py:193](../../../bt_api/bt_api_ctp/src/bt_api_ctp/collector/cli.py:193)、[instrument_provider.py:82](../../../bt_api/bt_api_ctp/src/bt_api_ctp/collector_ctp/instrument_provider.py:82) | 每个分片进程占 1 个 TD 会话（代码注释已承认会耗尽并发会话配额）；建议预导出合约清单、多进程共享静态清单，TD 只连一次 |
| 3 | 重连无退避 | [client.py:957](../../../bt_api/bt_api_ctp/src/bt_api_ctp/ctp/client.py:957) | 撞上 `ConnectFreq` 后会被反复踢，需指数退避（对应 P1-3） |
| 4 | 分片校验只到交易所粒度 | `--validate-shards`（[cli.py:235](../../../bt_api/bt_api_ctp/src/bt_api_ctp/collector/cli.py:235)） | 引入"连接"维度后，校验需回答"每连接合约数是否超 N、连接间是否重叠" |

落盘侧已具备多进程共享同一 `data_root` 的条件：[sink.py:203](../../../bt_api/bt_api_ctp/src/bt_api_ctp/collector/sink.py:203) 有 `fcntl` 跨进程文件锁，[sink.py:193](../../../bt_api/bt_api_ctp/src/bt_api_ctp/collector/sink.py:193) 临时文件名带 pid+uuid。分片正确（无重叠）时本就不会写同一文件。

### 6.4 分片落地建议

1. **优先"单机多进程 × 多账号"**，而非"单进程多实例"：隔离性、可观测性、可单独重启都更好，且天然规避坑 1。
2. **每连接订阅量 ≤ N**，N 由 P0-2 实验确定，不拍脑袋。
3. **合约清单预导出 + 共享**：TD 只连一次（或离线导出 JSON），MD 连接只负责订阅，避免 TD 会话配额被多分片吃掉。
4. 若必须同进程多实例，则每连接使用独立 flow 目录。
5. **决策顺序不能反**：先确认账号可开几个会话 → 再定每连接订阅量 → 最后定分片数。
6. 若券商能提供**按交易所分组的行情前置**，分片天然按"前置 ↔ 交易所"切分，比 `hash_mod` 更简单也更稳；需向券商索取前置清单。

### 6.5 需向券商 / SimNow 确认的问题

| # | 问题 | 影响 |
|---|------|------|
| Q1 | 本账号「同一用户最大允许在线会话数」是多少？行情系统与交易系统是否分别配置、分别是多少？ | 决定单机可开几个连接、多分片能否共用账号 |
| Q2 | 行情前置是否按交易所分组？请提供全部可用 MD 前置地址清单（含主备） | 决定分片能否按前置切分 |
| Q3 | 单账号行情订阅总量是否有配额？单连接建议上限是多少？ | 决定每连接订阅量 N 的取值 |
| Q4 | `ConnectFreq` 配置值是多少？本机出网 IP 能否加入 `whiteiplist`？ | 决定重连退避策略与稳定性 |
| Q5 | 是否提供行情组播（`ReqQryMulticastInstrument`）？ | 若开放，可绕开单连接订阅量瓶颈 |

### 重连重订阅契约（硬性约束，P1-3 的验收依据）

**触发场景**：`OnFrontConnected` → `OnRspUserLogin` 登录成功 → 恢复订阅 `_pending_instruments`（[client.py:964](../../../bt_api/bt_api_ctp/src/bt_api_ctp/ctp/client.py:964)）。

**要求**：

1. **必须分批**：待订阅合约数 > `subscription.batch_size`（默认 100）时，必须按 `batch_size` 切片逐次调用 `SubscribeMarketData`，**不得单次提交全量**。批次大小与批间间隔均取 `subscription` 配置，算法与 `subscribe_batched`（[client.py:1187](../../../bt_api/bt_api_ctp/src/bt_api_ctp/ctp/client.py:1187)）保持一致。
2. **批间限速**：批与批之间按 `subscription.batch_interval_sec`（默认 0.1s）间隔，避免 170 批瞬时打完。该约束由配置层强制：`validate_config` 拒绝 `batch_size < 1` 与 `batch_interval_sec <= 0`（含非数值）。库层默认仍允许 0，仅供离线测试使用。
3. **禁止阻塞 CTP 回调线程（关键）**：分批提交与批间等待必须在**独立订阅线程 / 任务队列**中执行。`OnRspUserLogin` 内只允许"标记待重订阅 + 唤醒订阅线程"，**不得在回调线程内 `sleep`**。
   - 依据：`OnRspUserLogin` 运行在 CTP 原生回调线程（[client.py:964](../../../bt_api/bt_api_ctp/src/bt_api_ctp/ctp/client.py:964)）。16,956 个合约按 100/批 + 0.1s 间隔 = 170 批 ≈ **17 秒**；在回调线程内等待会阻塞心跳与行情回调，直接触发 `OnFrontDisconnected`（reason `0x2001` 接收心跳超时）——即本轮观测到的断线形态。
   - 因此：**不允许把 `subscribe_batched` 直接搬进 `OnRspUserLogin`**；分批化必须与异步化同时完成，否则比现状更糟。
4. **失败记录与重试语义**（v1.4 修订）：**重连后必须重新提交全量**——前置在断线时会丢失全部订阅，不存在"只补差额"的形式；因此"只重试该批"仅适用于**会话内**的订阅失败。会话内失败的合约必须按 `instrument + error code` 记录（`failed_instruments`），由后续重订阅周期覆盖重试；失败清单在收到成功响应后必须清除。
   - 重连**退避不由采集侧实现**：重连时机由 CTP 原生库自动控制，本层无法节流；可控制的是重订阅节奏（分批 + 批间隔 + 可取消），见第 6.1 节 `ConnectFreq`。
5. **可观测**：重订阅过程输出 `generation / requested / submitted_batches / elapsed`，并连同 `failed_instruments` 写入 `report.json`。
   - `acked/failed` 无法按周期归属：`OnRspSubMarketData` 响应在提交后数分钟才陆续到达，日志与报告只能给出**会话累计**的 ok/failed；按周期的精确归属需要额外的时间窗统计，不在本批范围。
6. **必须可取消**（v1.4 新增）：分批提交必须支持在批边界中断（`should_stop` 谓词），`close()` 置停止位后再 `stop()` 客户端；否则一次 17 秒的分批循环会让 `Release()` 与在途原生调用竞态。
7. **首次登录不得触发重订阅**（v1.4 新增）：只有"关闭了一个断线窗口"的登录才算重连；首次登录必须不重复提交调用方的初次订阅，否则启动即产生双倍订阅风暴。

### 落盘读写模型与异步化契约（P1-5 / P1-6 的验收依据）

> v1.5 说明：本节已按**已实施**的设计重写。原稿假设"收盘一次性合并"，实施评估发现全市场单日 660 万行若一次性载入会占 GB 级内存、按合约逐个合并又会产生百万级读放大，因此改为**段文件 + 按批压缩**（见下）。

**改造前模型（事实，2026-09-17 实测）**：采集为单进程 + 单线程读写，`collector/` 内无任何落盘后台线程：

| 层级 | 职责 | 是否做 IO |
|------|------|----------|
| CTP 原生回调线程 | `OnRtnDepthMarketData` → normalize → `TickBuffer.append` | 无 |
| 主线程 | 主循环 flush、退出 flush、收盘 `finalize` | **全部读写** |
| 落盘临界区 | 每次 flush 对每个合约做 read → dedup → 整文件重写 | 读 + 写 |

后果：1,911 次 flush 触发 **463,897 次整文件重写**（近似二次方），主循环被单次 flush 阻塞最长 348 秒。

**改造后模型（已实施）**：

| 阶段 | 行为 | 成本 |
|------|------|------|
| 盘中 `write()` | 每个刷盘批追加**一个段文件** `<root>/.staging/<run_id>/<seq>.parquet`，不读任何已有文件 | O(本批行数) |
| 压缩（后台线程） | 待压缩段数 ≥ `sink.compact_segments`（默认 64）时，把这批段合并成最终文件；只处理**单合约**的 Python 行对象，内存有界 | 每批 = N 个段 |
| 收盘 `finalize()` | 等待后台压缩收尾 → 排空剩余段 → 认领崩溃运行遗留的段 → 生成报告 | 剩余段 |

关键性质：
- **最终文件重写次数与刷盘次数解耦**：单合约每天被重写 ≈ `总段数 / compact_segments` 次（默认约 30 次，对比改造前 1,911 次）。
- **磁盘即队列**：段文件本身就是待处理队列，不需要内存队列，也**不存在丢弃**；积压上限由磁盘容量决定。
- **崩溃可恢复**：段文件是完整 Parquet；压缩失败或进程被硬杀时段仍保留，`finalize()` 与后续运行都会认领（`_pid_is_alive` 判定属主进程是否已死，绝不碰存活进程的段）。
- **跨进程锁只在压缩时持有**，盘中写入完全无锁。

**方案取舍（供追溯）**：

| 方案 | 内容 | 结论 |
|------|------|------|
| A（**已采用**） | 段文件 + 按批压缩 + 压缩后台线程 | 内存有界、无读放大、改动可控；重写次数降到 `段数/N` |
| B | 收盘 k 路归并（段按 instrument+时间排序） | 可做到单合约只写 1 次，但需 ~2000 路归并（超 macOS 默认 fd 上限）与分轮次合并，实现量与风险最大；本期不做 |
| C | 落盘独立进程 | 链路最长，本期不做 |

**必须同时满足的要求（实施后修订）**：

1. **批量上限**：一次压缩处理的段数固定为 `sink.compact_segments`，内存与批大小绑定，不随当日累计数据增长。
2. **退出语义**：`finalize()` 必须"等后台压缩收尾 → 排空剩余段 → 生成报告"，不得丢尾批；排空采用"失败即停 + 段留在盘上"，不空转重试。
3. **异常可见**：段写入异常仍在调用栈上抛出（采集侧按原逻辑退回缓冲）；压缩异常在后台线程记录 `ERROR` 日志、计数并保留段，`report.json` 输出 `compaction_failures`，收盘自动重试。
4. **跨进程锁范围**：`_instrument_lock` 只覆盖最终合并；盘中写入不持锁。
5. **`finalize` 报告开销**：仍按现状全量扫当日最终文件生成逐合约统计（未在本批优化，见遗留项）。
6. **内存预算**：未落盘数据 = `TickBuffer` + 正在压缩的一批段（Arrow）。磁盘上的待压缩段不计入内存。
7. **不指望 GIL 换线程提速**：段写入是 O(批) 的 pyarrow 写；压缩慢的原因是 `_dedup_sort` 纯 Python 循环，因此把压缩移出主线程只为不阻塞采集，不为提速。

## 8. 验收标准修订建议

现有 AC 只验证"链路可跑通 + 字段正确 + 去重排序正确 + 路径正确"，无法区分"数据可用"与"数据几乎为空"。建议新增/收紧：

| 项 | 建议判据 |
|----|----------|
| 数据完整性（新增） | 主力合约在连续交易时段内的 500ms 覆盖率 ≥ 99% |
| 成交量连续性（新增） | 相邻快照 volume 增量异常率 ≤ 0.1%（异常定义：增量 > 该合约近 1 分钟成交量分位阈值） |
| 断线可观测（收紧 AC-2 / 可靠性） | 运行日志中每次断线/恢复有成对记录；`report.json` 含断线时间窗 |
| 订阅就绪（收紧 AC-2） | 日志给出 `requested / acked / timed_out`，运营可按 acked 比例判断就绪 |
| 重连重订阅分批（新增） | 重连后单次原生 `SubscribeMarketData` 的参数长度 ≤ `subscription.batch_size`；重订阅不在 CTP 回调线程内执行（`OnRspUserLogin` 返回 < 1s） |
| 落盘时延与写放大（新增） | flush 不阻塞心跳（无 >2× `heartbeat_interval_sec` 的空档）；单日单合约文件重写次数 = 1 |
| 数据可用性（收紧数据质量） | "抽样人工核对"改为必做项，且核对对象包含成交量连续性 |
| 环境标注（新增） | 验收结论必须标注环境（SimNow / 生产），SimNow 上的结果不得作为"全市场采集能力"的证据 |

同时建议：在 `验收文档.md` 中把本轮（2026-09-17）的结论从"通过"修订为"链路通过、数据完整性未通过"，并把本文档第 3 节证据作为附件引用。

**关键设计取舍**：

1. **P2-1 选择"丢弃"而不是"加 schema 列"**：新增列会改变已固定的落盘 schema（NFR-5），影响所有下游读取方；而订阅时伪快照（实测 4,757 个合约共享同一时间戳）本就不是行情数据。丢弃值可关闭，且计数可查。
2. **P2-5 的分母用"窗口内交易秒数"**而非"当日全部交易秒数"：冷门合约整天只出几条数，用全天做分母会把"品种不活跃"误判成"采集缺失"；用其自身首末快照覆盖的时段做分母，衡量的是"它在活跃期间被采到了多少"。
3. **P0-5 的静默判定只统计"最近活跃过"的合约**（参考窗口 = 3 × `silent_after_sec`）：否则尾盘时大量"上午活跃、下午本就安静"的合约会把静默占比推到阈值以上，造成必然误报。
4. **自适应阈值以 `max()` 与配置下限结合**，且要求 ≥ 5 个间隔样本：仅对慢速合约放宽（消除误报），不会让快速合约变迟钝，样本不足时退回固定阈值。

## 附录 A：核验方法（可复现）

以下检查不依赖运行进程，直接读落盘数据与日志：

1. **覆盖率**：对目标合约，取连续时段（如白盘 09:30–10:14）内 `update_time` 计数，除以 `时段秒数 / 0.5`。
   基准需先在健康窗口验证（本次用 `zn2705` 夜盘 23:00–01:00，中位间隔 0.5s）。
2. **成交量连续性**：按 `(action_day, update_time, update_millisec)` 排序后，统计相邻 `volume` 增量；异常增量即丢失快照的区间。
3. **断线痕迹**：
   - 日志侧：`grep -c "OnSessionDisconnected" collector.log`；
   - 计数侧：心跳 `sub_ok` 出现 ≈16,956 的整轮阶梯增长即代表一次重连重订阅；
   - 日志饥饿：相邻心跳时间差 > 90s 即为 flush 阻塞。
4. **缺口分布**：按 `report.json` 的 `gaps.before` 分桶，同一分钟出现数百上千个合约即全局停摆窗口。
