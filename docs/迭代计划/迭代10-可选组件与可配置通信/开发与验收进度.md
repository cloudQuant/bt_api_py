## 第02轮：认证通信、注册表和 SDK 代理

本轮在现有 dev 中接通“解析配置 → 部署图检查 → CURVE 认证 → 服务注册 → 受权 RPC → 续租/注销”。领域组件的真实装配是下一轮；本轮集成使用实际子进程、socket、ZAP、SQLite 和合成账户读取处理器。

### 交付内容

- `service_deployment.validate_deployment`：离线检查跨服务依赖环、目标实例/端口、账户写入口冲突和 RPC/行情双端点匹配，输出冻结的启动顺序。market 配置现在同时需要 RPC 控制端点与行情端点。
- `service_registry.ServiceRegistry`：可信 principal 与 wire 身份逐项匹配、scope/动作授权、SQLite 幂等注册、租约、重启 epoch、数据库进程持有锁、同一策略/账户的单活写会话。注销和租约结束只处理登记，不修改交易账本。多账户声明先整体检查后整体写入。
- `service_runtime.ServiceClientRuntime`：按配置选择代码登记的代理动作，查询远端能力、申请注册、精确选择账户、显式续租和关闭。必需依赖失败回收本轮登记，可选遥测/监控控制失败报告降级；监控查询能力可以继续使用。回执校验失败也回收已取得的注册句柄，注销回执不完整会计入清理失败。
- `ZmqServiceClient/Server`：所有 TCP（含 loopback）强制 CURVE/ZAP，授权身份取自认证帧的 User-Id。回复用该认证客户端公钥进行 libsodium SealedBox 加密，防止断线后不同密钥复用 ROUTER ID 读取原回复；版本前缀和 48 字节加密开销计入帧限额，不接受明文降级。
- 消息接收限制帧数并分批丢弃多余帧；断线目标、队列满和无法容纳的错误回复不会导致重复业务派发。已发送请求超时或回复失配返回 UNKNOWN，退役该连接；连接内最多记录4096个请求 ID，拒绝重复 ID。确定未排队的请求返回 NOT_SENT，允许调用者显式再次请求；传输层均不自动重试。

处理器异常或非可信错误回执不证明业务没有副作用，SDK 对此返回 BUSINESS_OUTCOME_UNKNOWN。业务作用域和 transport ID 分开：未知订单结果仍需使用业务订单/幂等键向领域服务核对，不能仅换一个 message_id 再下单。注册成功也不代表策略恢复完数据基线或可以交易。

以上适配器借用资源，显式授权映射之外的账户、策略、执行域或组合不会被猜测、扩展或聚合。具有明确 strategy 的模板可接受该策略不同 run_id；Gateway 仍读取同一持久策略流，不能据此声称日志按 run 隔离。账户范围读取需要显式目标，当前各适配器的组合/人工 book 支持范围不同，尚不代表 AFI 全部视图可用。

### 宿主装配与本轮验收状态

SDK 的 `ServiceHost` / `TrustedServiceAuthority` 与 `ComponentResources` 已接通。宿主构造不打开文件或连接；启动先完成引用、所有选中组件、ACL/capability 关系及 ZMQ endpoint/CURVE keypair 的纯校验，再按依赖获取资源、创建未就绪注册表、登记处理器并绑定认证监听，最后声明就绪。端口只声明实际实现的动作；Risk 的操作集从其实际类属性读取，不依赖不存在的模块常量。

就绪状态在等待请求前和实际派发前重新检查，未就绪时拒绝业务调用及新增/续期登记，仍允许发现和注销。清理先停止对外就绪和监听，再逆序释放本宿主拥有的组件，最后关闭注册表；借用资源保持调用方所有。关闭失败保留资源和 `close_failed` 状态，后续显式 close 只重试未完成项。owned 资源的关闭回调必须可安全重试。

Transport 服务端按 authenticator → socket → context 关闭，依赖资源关闭失败时不继续阻塞式 context.term；部分关闭后禁止继续请求或服务。服务端构造失败且清理失败用 `ServiceTransportStartupCleanupError.transport` 将部分实例交给宿主，包含启动期间中断的清理分支。注册表的对应异常携带 `.registry`；数据库和锁文件关闭成功后才清引用，锁文件已关闭后抛错也可完成下一次清理。正常启动异常在清理成功后仍传播，不伪装启动成功。

出站服务 clients 暂时只做完整部署图检查，然后明确拒绝未接通的运行装配；不会忽略配置。可信资源提供器仍由部署方代码实现，本轮没有提供通用私密配置加载器或部署 CLI。现有 account-service.yaml 是完整目标配置的离线样例，其中的交易写端口尚不能由本轮读取宿主启动。

### 行为和使用合同

Gateway 的 `read_for_consumer` 在同一 SQLite 事务内读取快照/事件和持久化本次可返回范围。进度按 principal、可信 consumer_ref、账户和视图隔离，包含持久的 `stream_epoch`、`offered_cursor` 和 `acknowledged_cursor`。流代次在同一库重开后保持，与服务进程代次和 provider session generation 分开；重建流不得沿用旧代次重置序号。

`offered_cursor` 表示已准备返回的数据范围，不证明网络实际送达。正游标续读必须提供匹配代次，且不能跳过此前未向该消费者提供的范围；从零读取或显式 `cursor=None` 基线读取可启动消费。保留期内可重放；已压缩部分返回新快照及后续事件，接收方必须先应用基线。服务端只保存有界消费者/流记录（各最多8192）；上限只拒绝新增，不阻止已有消费者继续。

ACK 只能确认该消费者已提供范围以内的游标；重复或更早 ACK 返回当前进度，不回退。错误代次、未来游标和未授权范围拒绝，失败事务不留下新进度。ACK 只改变消费元数据，不删除源事件、快照或去重记录，不确认交易所订单、不释放风险、不提升账户就绪。进度查询不隐式创建消费者。

服务端从 registry 的已认证 WireIdentity 与授权视图派生 consumer_ref，包含角色/principal/actor/delegate 和执行域/账户/策略，不含 run_id 或 registration_id。同一逻辑消费者的新运行可以续用，不同 actor、委托、角色或策略保持隔离；客户端不能提交任意 consumer ID。直接 Python 调用该适配器仍须由调用方提供可信上下文，它本身不是认证层。

SDK 仍通过既有 `ServiceClientRuntime.call` 使用账户端口：

- 显式申请并授权 `account.read_after`、`account.ack` 和 `account.progress`。
- 首读 `account.read_after` 使用 `track_delivery: true`、`cursor: 0` 和有界 limit；回复附 `consumer_progress`。
- 接收方本地业务投影和游标同事务落盘后，才用回复中的 stream_epoch 与已保存 cursor 调 `account.ack`。
- 后续以本地恢复点和对应 stream_epoch 续读；`account.progress` 仅供核对，不能替代接收方自己的事务恢复点。

旧客户端未显式申请新操作时仍只登记原来的 snapshot/head/read_after，避免服务升级后自动申请新的 ACK 权限。未跟踪 read_after 保持原响应形状，不写消费者状态；普通 snapshot/head 不变。ACK 是自己的消费记录写入，不成为交易 writer 能力，操作依旧需要明确 grant。领域错误沿用现有 registry 的 HANDLER_FAILED 封装，Python 直调保留有限错误码；可操作的跨组件错误合同仍需后续补齐。

### 服务生产者如何使用

部署端显式注册 `upstream.telemetry / events.append`，在已经启动的 SERVICE runtime 所属线程中创建 sink。sink 用 scope_ref 选择唯一注册目标，本地 outbox_scope 只限制可消费的本地队列，不参与远端授权。相同 runtime 可以按不同 scope_ref 创建多个 sink，分别管理账户/目的地的游标；同一 selector 对应多个目标则拒绝。

```python
from bt_api_monitor.durable import DurableOutbox, DurableOutboxConsumer
from bt_api_py.service_monitor import ServiceMonitorOutboxSink

# runtime 已按部署配置启动，并显式申请 events.append。
outbox = DurableOutbox(producer_outbox_path)
sink = ServiceMonitorOutboxSink(
    runtime, scope_ref=monitor_scope_ref, outbox_scope=producer_scope,
)
consumer = DurableOutboxConsumer(
    outbox, consumer_id=sink.consumer_id, scope=sink.outbox_scope, deliver=sink,
)
# 业务方先用 outbox.append_bounded(event, max_events=..., max_bytes=...)
# 持久化脱敏事件；以下两行由同一 owner thread 的受监督循环定期调用。
runtime.maintain()
consumer.consume(limit=100)
```

sink 不拥有 runtime，不启动线程，不安排重试，也不替调用方关闭资源。若借用 ServiceHost.upstream，使用 TrustedServiceClients.requested_operations 显式选择持久操作，并由既有 host 生命周期维护/关闭 upstream；投递仍由同一 owner loop 显式调用。未配置 Monitor 的路径不会创建这些对象；导入新 SDK 模块不应导入四组件或 ZMQ 后端。

sink.consumer_id 绑定稳定 producer identity（含 delegate）、目的服务/实例/scope_ref、完整业务 scope 和本地 outbox scope；排除 run_id、registration_id 和 service_epoch，使正常重启保持游标。运行中的 sink 仍检查完整 scope 和短期注册代次，RPC 前后改绑不得确认本地事件。改变逻辑目的地会生成独立游标；沿用同一逻辑服务身份部署新库时，运维仍须迁移已确认数据，不能依赖客户端 checkpoint 重建已丢失的远端历史。

只有精确三字段持久回执通过验证后 callback 才返回：source_event_id 必须对应当前源事件，服务端 ID 必须符合 namespaced hash 格式，sequence 必须为有效正整数。远端 sequence 与本地序号不同；已有 DurableOutboxConsumer 仍只确认源 item.sequence。RPC 异常、未知结果、无效回执、本地 checkpoint 写入失败均保留待发事件；按策略恢复 runtime、重新创建 sink/consumer，再用同一 ID 和内容显式消费。异常不能被吞掉后当作成功。

这一条链路只提供至少一次投递与接收端稳定 ID 去重。producer 业务状态与 outbox 不共享事务；接收端持久化与本地确认也不共享事务。源 scope 的事件类型必须属于目标 allowlist，一个不可接收事件会阻塞后续有序项，不能静默跳过。两个 outbox 均需容量政策，ACK 不删除历史；本轮不加入 retention/GC、普通策略指标队列、告警或交易控制。

### 行为与使用边界

样本合同固定八个字段，拒绝未知字段、重复键与非法结构：`stream_id`（≤64字节、无空白可打印字符）、`sequence`（1..2^63-1）、`kind` 仅为 `heartbeat` 或 `metrics`、`observed_at` 必须是可表示的有限数值、最多32个扁平数值指标（名称按 ASCII 标识符校验并拒绝含 secret/token/password/credential/apikey/privatekey 的名称）、两个丢弃计数（0..2^63-1）。心跳不得携带指标，指标样本不得为空；规范化 JSON 超过8192字节即拒绝。这是普通遥测的线上合同，不是经济事实、账户新鲜度或可交易性的证明。

发射器 `ServiceTelemetryEmitter` 只拥有自己的内存队列，借用调用方已创建并持有的 `ServiceClientRuntime`：不建线程、不注册或注销、不关闭 runtime、不安排重试。`enqueue_heartbeat`／`enqueue_metrics` 不做任何 I/O，队列按条数和编码字节双重设限（默认64条／64 KiB，硬上限4096条／4 MiB），溢出丢弃最新样本并递增队列丢弃计数；`flush` 只能在 runtime 的 owner thread 调用，逐条投递并在首个失败处停止，失败、回执不合法或结果未知的样本被丢弃并计入投递丢弃计数，后续样本继续留在队列。丢弃计数在下一条样本上报，因此消费者看到的是“此前发生过多少丢弃”，而不是补齐历史。

绑定必须是可选的 `runtime.telemetry` 且被固定：身份、完整绑定签名、授权操作或路由就绪状态在投递前后任一变化，样本即被丢弃而不发送。回执必须是精确的三字段 `stream_id`／`sequence`／`accepted`，且与当前样本一致。`close` 只丢弃本发射器自己的队列，不触碰借用 runtime；策略侧进程不导入 gateway／monitor／risk／execution 或 ZMQ 后端。

Monitor 的 `telemetry_ingress` 角色只绑定 `service.telemetry_ingress`（`telemetry.append`）与 `service.monitor_query`（`telemetry.snapshot`）；旧的 roleless Monitor 仍只有 `monitor.query`／`monitor.read_after`，`durable_ingress` 不变，因此普通遥测角色不会给既有读取路径扩权。服务端按 `(可信身份, scope, stream_id)` 保存每个流的最新投影，序号回退拒绝，完全相同的重发返回原回执且不延长新鲜度，同序号不同内容判为冲突。容量按流数与保留逻辑字节在写入前判定，过期流释放容量；`telemetry.snapshot` 只返回授权 scope 内的有界结果，超过900 KiB 或超出传输回复预算即显式失败。新鲜度来自服务端单调时钟的接收时间，只有心跳才算健康；这些观察全部在内存中，重启即丢失，必须由生产者重新采集，不能当作持久补传。

配置侧只为 monitor 客户端别名开放 `telemetry_queue_max_events`（1..4096）与 `telemetry_queue_max_bytes`（1..4 MiB），其他别名继续拒绝这两个字段。注册表把 `ServiceResultTooLargeError` 映射为 `REPLY_TOO_LARGE` 的分支增加 `(service.monitor_query, telemetry.snapshot)`，与账户读取同样在有界回复预算外显式失败，而不是截断结果。

回执必须严格匹配字段集合与标量类型，任何多余或缺失字段、非有限数值、类型不符、以及 intent/cancel 标识与请求不一致都会被拒绝为 `INVALID_REPLY`。`UNKNOWN` 是正常返回值，代表 provider 结果待对账；只有 RPC 本身不确定时才抛 `ServiceExecutionUnknownOutcomeError`（携带业务标识），调用方必须用 `query` 对账而不能直接重发同一标识。可证明未发出的请求区分报 `REQUEST_NOT_SENT`，其余传输异常按"可能已到达"处理。远端业务拒绝（如 `INTENT_CONFLICT`）携带既有记录时作为 `ServiceExecutionError.record` 返回。

与远端回执 sequence 独立，后者不能替代源游标。每条远端持久回执确认后，
复核此次源行仍相同，才用短 CAS 事务推进游标；RPC 期间不持有源/游标数据库事务。当前游标的
源行消失、内容改变或同代次日志回退会停止投递，不清零游标。并发同事件确认幂等，较新或冲突
确认不能回退游标；发送失败/回执不确定/本地写失败保留同事件重放。游标库限制4096个命名空间
和2048个SQLite页，不代表源 journal 或长期磁盘占用已有完整治理。

投影仅含固定生命周期元数据、精确纳秒时间和可信的 provider/环境/账户/策略/交易日归属。
外层类型是 `execution.lifecycle` 与 `execution.cancellation`；原业务事件类型作为有界元数据
保留，不解释金额/手续费/余额/PnL。账户和可选策略必须与已授权 WireScope 匹配；拒绝本轮无法
过滤的多账户集合、portfolio、group、leg、manual book 限制。Monitor 外层 source_event_id 是
确定性的投影 ID，原 Execution UUID 保存在 payload 内，二者在测试与文档中明确区分。

使用与关闭顺序见 `docs/guides/execution-monitor-relay.md`。relay.close 不关闭借用的 reader/
runtime；runtime 恢复注册后需显式 rebind，稳定目标变化拒绝继承旧游标。未交付新的独立 CLI/
supervisor、源日志 retention/压缩/磁盘配额、Gateway/Risk 全量业务 producer 或组合风控规则。
