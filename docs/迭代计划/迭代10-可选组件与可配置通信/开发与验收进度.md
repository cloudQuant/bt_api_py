## 第02轮：认证通信、注册表和 SDK 代理

本轮在现有 dev 中接通“解析配置 → 部署图检查 → CURVE 认证 → 服务注册 → 受权 RPC → 续租/注销”。领域组件的真实装配是下一轮；本轮集成使用实际子进程、socket、ZAP、SQLite 和合成账户读取处理器。

### 交付内容

- `service_deployment.validate_deployment`：离线检查跨服务依赖环、目标实例/端口、账户写入口冲突和 RPC/行情双端点匹配，输出冻结的启动顺序。market 配置现在同时需要 RPC 控制端点与行情端点。
- `service_registry.ServiceRegistry`：可信 principal 与 wire 身份逐项匹配、scope/动作授权、SQLite 幂等注册、租约、重启 epoch、数据库进程持有锁、同一策略/账户的单活写会话。注销和租约结束只处理登记，不修改交易账本。多账户声明先整体检查后整体写入。
- `service_runtime.ServiceClientRuntime`：按配置选择代码登记的代理动作，查询远端能力、申请注册、精确选择账户、显式续租和关闭。必需依赖失败回收本轮登记，可选遥测/监控控制失败报告降级；监控查询能力可以继续使用。回执校验失败也回收已取得的注册句柄，注销回执不完整会计入清理失败。
- `ZmqServiceClient/Server`：所有 TCP（含 loopback）强制 CURVE/ZAP，授权身份取自认证帧的 User-Id。回复用该认证客户端公钥进行 libsodium SealedBox 加密，防止断线后不同密钥复用 ROUTER ID 读取原回复；版本前缀和 48 字节加密开销计入帧限额，不接受明文降级。
- 消息接收限制帧数并分批丢弃多余帧；断线目标、队列满和无法容纳的错误回复不会导致重复业务派发。已发送请求超时或回复失配返回 UNKNOWN，退役该连接；连接内最多记录4096个请求 ID，拒绝重复 ID。确定未排队的请求返回 NOT_SENT，允许调用者显式再次请求；传输层均不自动重试。

处理器异常或非可信错误回执不证明业务没有副作用，SDK 对此返回 BUSINESS_OUTCOME_UNKNOWN。业务作用域和 transport ID 分开：未知订单结果仍需使用业务订单/幂等键向领域服务核对，不能仅换一个 message_id 再下单。注册成功也不代表策略恢复完数据基线或可以交易。

以上适配器借用资源，显式授权映射之外的账户、策略、执行域或组合不会被猜测、扩展或聚合。具有明确 strategy 的模板可接受该策略不同 run_id；Gateway 仍读取同一持久策略流，不能据此声称日志按 run 隔离。账户范围读取需要显式目标，当前各适配器的组合/人工 book 支持范围不同，尚不代表 AFI 全部视图可用。

### 宿主装配与本轮验收状态

SDK 的 `ServiceHost` / `TrustedServiceAuthority` 与 `ComponentResources` 已接通。宿主构造不打开文件或连接；启动先完成引用、所有选中组件、ACL/capability 关系及 ZMQ endpoint/CURVE keypair 的纯校验，再按依赖获取资源、创建未就绪注册表、登记处理器并绑定认证监听，最后声明就绪。端口只声明实际实现的动作；Risk 的操作集从其实际类属性读取，不依赖不存在的模块常量。

就绪状态在等待请求前和实际派发前重新检查，未就绪时拒绝业务调用及新增/续期登记，仍允许发现和注销。清理先停止对外就绪和监听，再逆序释放本宿主拥有的组件，最后关闭注册表；借用资源保持调用方所有。关闭失败保留资源和 `close_failed` 状态，后续显式 close 只重试未完成项。owned 资源的关闭回调必须可安全重试。

Transport 服务端按 authenticator → socket → context 关闭，依赖资源关闭失败时不继续阻塞式 context.term；部分关闭后禁止继续请求或服务。服务端构造失败且清理失败用 `ServiceTransportStartupCleanupError.transport` 将部分实例交给宿主，包含启动期间中断的清理分支。注册表的对应异常携带 `.registry`；数据库和锁文件关闭成功后才清引用，锁文件已关闭后抛错也可完成下一次清理。正常启动异常在清理成功后仍传播，不伪装启动成功。

出站服务 clients 暂时只做完整部署图检查，然后明确拒绝未接通的运行装配；不会忽略配置。可信资源提供器仍由部署方代码实现，本轮没有提供通用私密配置加载器或部署 CLI。现有 account-service.yaml 是完整目标配置的离线样例，其中的交易写端口尚不能由本轮读取宿主启动。

### 行为和使用合同

Gateway 的 `read_for_consumer` 在同一 SQLite 事务内读取快照/事件和持久化本次可返回范围。进度按 principal、可信 consumer_ref、账户和视图隔离，包含持久的 `stream_epoch`、`offered_cursor` 和 `acknowledged_cursor`。流代次在同一库重开后保持，与服务进程代次和 provider session generation 分开；重建流不得沿用旧代次重置序号。

`offered_cursor` 表示已准备返回的数据范围，不证明网络实际送达。正游标续读必须提供匹配代次，且不能跳过此前未向该消费者提供的范围；从零读取或显式 `cursor=None` 基线读取可启动消费。保留期内可重放；已压缩部分返回新快照及后续事件，接收方必须先应用基线。服务端只保存有界消费者/流记录（各最多8192）；上限只拒绝新增，不阻止已有消费者继续。

ACK 只能确认该消费者已提供范围以内的游标；重复或更早 ACK 返回当前进度，不回退。错误代次、未来游标和未授权范围拒绝，失败事务不留下新进度。ACK 只改变消费元数据，不删除源事件、快照或去重记录，不确认交易所订单、不释放风险、不提升账户就绪。进度查询不隐式创建消费者。

服务端从 registry 的已认证 WireIdentity 与授权视图派生 consumer_ref，包含角色/principal/actor/delegate 和执行域/账户/策略，不含 run_id 或 registration_id。同一逻辑消费者的新运行可以续用，不同 actor、委托、角色或策略保持隔离；客户端不能提交任意 consumer ID。直接 Python 调用该适配器仍须由调用方提供可信上下文，它本身不是认证层。

SDK 仍通过既有 `ServiceClientRuntime.call` 使用账户端口：

- 显式申请并授权 `account.read_after`、`account.ack` 和 `account.progress`。
- 首读 `account.read_after` 使用 `track_delivery: true`、`cursor: 0` 和有界 limit；回复附 `consumer_progress`。
- 接收方本地业务投影和游标同事务落盘后，才用回复中的 stream_epoch 与已保存 cursor 调 `account.ack`。
- 后续以本地恢复点和对应 stream_epoch 续读；`account.progress` 仅供核对，不能替代接收方自己的事务恢复点。

旧客户端未显式申请新操作时仍只登记原来的 snapshot/head/read_after，避免服务升级后自动申请新的 ACK 权限。未跟踪 read_after 保持原响应形状，不写消费者状态；普通 snapshot/head 不变。ACK 是自己的消费记录写入，不成为交易 writer 能力，操作依旧需要明确 grant。领域错误沿用现有 registry 的 HANDLER_FAILED 封装，Python 直调保留有限错误码；可操作的跨组件错误合同仍需后续补齐。

### 配置、权限与持久化合同

原来的默认 Monitor 仍是只读查询。显式选择 `options.role: durable_ingress` 才装配持久入口，唯一端口为 `service.telemetry_ingress`，唯一操作为 `events.append`。普通 `telemetry.append` 与持久事件操作使用不同 grant；SDK 默认注册仍只申请前者，服务 producer 必须用 requested_operations 显式申请后者。配置只含 role 时默认最多10000条、64 MiB保留逻辑内容、64 KiB单事件；三个限制可显式调小，并有代码硬上限。零配置没有新增线程、连接或可选包导入。

adapter 只接受经过 registry 认证和授权的 SERVICE 身份，principal 必须一致。scope 唯一匹配受信 target，event_type 必须属于该 target 的 allowlist。请求只含 schema_version=1、event_id、event_type、occurred_at、data；不能请求另一 scope、producer 或服务端 ID。服务端单独保存可信 producer 元数据和源事件 ID，再嵌入经过 JSON 深度/节点/字节限制及敏感字段拒绝的 payload。此处接收通用服务事件，不自动赋予经济事实完整性、策略归属、账户新鲜度或 PnL 权威。

稳定 ID 绑定 principal/actor/delegate、授权 scope、outbox 目标及源 event_id，按重启重放合同排除 run_id。生产者须跨运行保持源 ID 唯一，并保存原 ID/内容供重放；同一事件完全相同地重发，返回原持久 sequence，内容或时间变更则冲突，不覆盖。调用返回丢失或提交后异常仍是 BUSINESS_OUTCOME_UNKNOWN，没有自动重试；恢复 runtime 后由生产者显式重放原事件。本轮不实现生产者业务状态和待发 outbox 的同库事务。
