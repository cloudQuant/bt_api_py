## 1. 背景与目标

### 1.1 背景

量化研究与回测需要高质量的历史 tick 数据。当前项目 `bt_api_py` 已具备：

- CTP 插件包（`bt_api_ctp`）已接入行情，`live_ctp_feed.py` 能通过 `OnRtnDepthMarketData` 回调接收深度行情快照，ticker 容器 `CtpTickerData` 已完整支持期货与期权字段（`strike_price`、`option_type`、`underlying_instrument`、`open_interest` 等）。
- 已有历史 K 线下载能力（`bt_api_py/data_downloader.py`），但仅覆盖 K 线，不覆盖 tick。
- 项目已依赖 `pyarrow>=14.0.0`，具备 Parquet 列式落盘的基础。

但缺少一套**面向全市场 tick 数据采集、落盘、清洗、多机分片**的完整方案。本迭代旨在补齐这一能力。

### 1.2 目标

1. 通过 CTP 采集**国内六大期货交易所**（SHFE 上期所、DCE 大商所、CZCE 郑商所、CFFEX 中金所、INE 上海国际能源交易中心、GFEX 广期所）的**全部期货合约 + 全部期权合约**的**深度行情快照 tick 数据**。
2. 数据按 `按天 / 交易所 / 合约名` 的目录结构落盘为 Parquet 文件。
3. 提供可部署的采集脚本：**开盘前自动连接并订阅当日有效合约全集，盘中持续采集，收盘后清洗保存**。
4. 支持**多机分片**：不同服务器/本地电脑各自负责部分合约，收盘后各自本地完成清洗保存（本期不做自动跨机汇总）。
5. 接口设计**与交易所解耦**，为后续接入其他交易所（Binance、OKX 等）的 tick 数据预留扩展点。

### 1.3 非目标（本期明确不做）

- 不做跨机自动汇总/去重（仅本地保存，人工/后续迭代合并）。
- 不做逐笔成交/逐笔委托（需额外行情授权，绝大多数品种不提供）。
- 不做实时行情分发/回测引擎直接消费（本期只落盘）。
- 不重构 CTP 底层 SWIG/C++ 扩展（复用现有 `ctp_md_api.py`）。

## 2. 用户故事与场景

### US-1 采集脚本（核心用户）

> 作为一名量化研究员，我希望有一个命令行脚本，运行后能在每个交易日自动完成"连接 → 查询合约全集 → 订阅 → 采集 → 清洗落盘"的完整流程，而无需我手动干预。

### US-2 合约全集动态获取

> 作为采集系统，我需要在开盘前通过 CTP `ReqQryInstrument` 动态获取当日所有有效合约（含期货与期权），而不是依赖静态清单，因为期权合约每天大量新增、到期。

### US-3 深度行情快照

> 作为数据采集者，我需要把 CTP `OnRtnDepthMarketData` 回调的完整字段（盘口五档、最新价、成交量、持仓量、结算价、涨跌停等）逐条记录，保证数据完整性。

### US-4 分片与多机部署

> 作为运维者，我有几台服务器和本地电脑，希望把全市场合约**按某种策略分片**到不同机器，每台机器只采集自己分片内的合约，避免重复采集，收盘后各自独立完成清洗保存。

### US-5 数据路径规范

> 作为数据使用者，我希望数据文件路径稳定可预期：`<根目录>/<日期YYYYMMDD>/<交易所>/<合约名>.parquet`，便于后续程序化读取与合并。其中"日期"统一为 **trading_day（交易日）**：夜盘（21:00 起）的行情归属次日交易日的目录。

### US-6 扩展其他交易所

> 作为架构师，我希望采集框架的接口与 CTP 具体实现解耦，未来接入 Binance、OKX 等只需实现统一接口，不改动主流程。

## 3. 功能需求

### FR-1 合约全集查询

- 采集前通过 CTP 查询当日有效合约（`ReqQryInstrument` 或等价能力）。
- 合约需区分**期货**与**期权**；期权需保留 `underlying_instrument`、`strike_price`、`option_type`（看涨/看跌）。
- 合约需按**交易所**归类，直接使用查询返回的 `ExchangeID` 字段（SHFE/DCE/CZCE/CFFEX/INE/GFEX），不依赖合约代码前缀推断。
- 默认仅保留 `future` 与 `option` 两类合约用于订阅；合约全集还包含 combination（组合）、tas、spot/efp、mi 等其他类型（`ProductClass` 完整枚举见 `normalize_ctp_instrument`），默认排除、排除规则可配置。
- 查询失败需有重试与降级策略。

### FR-2 行情订阅

- 支持批量订阅（`SubscribeMarketData`），受 CTP 单次订阅数量限制影响，需**分批订阅**。
- 订阅成功后进入采集状态；订阅失败的合约需记录并可重试。
- 需处理行情连接断开、重连、重新订阅的完整生命周期。

### FR-3 tick 数据采集

- 每条 `OnRtnDepthMarketData` 回调需原样记录全部有效字段，不丢失、不裁剪。
- 需记录**本地接收时间戳**（`local_receive_time`，墙钟 UTC 纳秒）与**行情时间**（`action_day` + `update_time` + `update_millisec`，毫秒精度），用于后续时序对齐与去重；**毫秒字段不可省略**（CTP 快照为 500ms 级推送，同一秒内同合约可有多条快照）。
- 需同时记录 `trading_day`（交易日）与 `action_day`（业务发生日）两个字段：夜盘时段两者不一致（如周一 21:00 后的行情，`action_day` 为当日自然日、`trading_day` 为周二）。
- 需记录合约标识（`instrument_id`、`exchange_id`）。

### FR-4 内存缓冲与落盘

- 盘中 tick 高频产生，需内存缓冲（如按合约分桶的环形缓冲或追加缓冲区），避免每条 tick 直接写盘造成 IO 瓶颈。
- 缓冲需有**上限保护**（防止某合约异常刷量导致内存耗尽）。
- 定期（如每 N 秒）或缓冲达到阈值时批量刷盘。

### FR-5 收盘清洗保存

- 收盘后触发清洗：按 `按交易日/交易所/合约名` 组织数据，写 Parquet；目录日期统一采用 **`trading_day`**（与 CTP `GetTradingDay()` 一致），使夜盘数据归属其对应交易日。
- 清洗需包含：去重（按 `instrument_id + action_day + update_time + update_millisec`，同键多条保留 `local_receive_time` 最新一条）、时间排序（含毫秒）、字段类型规整。
- 需生成**采集完整性报告**（每个合约的 tick 条数、起止时间、是否有缺口，缺口含断线时间窗），便于核对。

### FR-6 定时调度

- 支持开盘前自动启动（如通过 cron / systemd timer / 脚本内置调度）。
- 调度需覆盖**夜盘**：夜盘 21:00 开始（最晚品种至次日 02:30），且**夜盘在交易日的前一晚进行**——**周五晚的夜盘与周一的日盘同属一个交易日**，**周日晚没有夜盘**；法定节假日前一交易日晚夜盘暂停。因此调度时点为"交易日当晚 20:45"（周一~周五，即夜盘调度用 `Mon..Fri` 而非"周日~周四"）与"交易日当天 08:45"，分别由 `--night` 与默认模式区分。
- 需内置交易日判断（区分工作日与交易日，避开节假日）；交易日权威口径以 CTP 登录后的 `GetTradingDay()` 为准，本地日历仅用于进程启动前预判与夜盘有无判断。
- 需支持手动触发模式（`--once`）便于开发调试与当日进程中断后的恢复（CTP 行情不可回放历史，**无法补采往日数据**）。

### FR-7 分片配置

- 通过配置文件声明**本机负责的交易所 + 合约范围**（如按合约代码前缀、按品种、按哈希取模分片）。
- 每台机器独立运行，互不依赖。
- 分片配置需可校验：提供校验命令（输入各机分片配置，校验"交集非空 / 并集存在覆盖缺口"并输出诊断），避免多机重复或遗漏。

### FR-8 接口抽象（跨交易所扩展）

- 定义交易所无关的采集接口（如 `TickCollector`、`InstrumentProvider`、`MarketDataSubscriber`），CTP 是首个实现。
- 主流程（调度、缓冲、清洗、落盘）与具体交易所实现解耦。

## 4. 非功能需求（NFR）

### NFR-1 性能（重点）

- **订阅规模**：全市场期货 + 期权合约数量可达数千个（期权尤多），需支持分批订阅且不阻塞行情接收。
- **吞吐**：行情高峰时多个合约同时推送 tick，需保证单机采集**不丢 tick**（回调内只做轻量操作，重活异步）。
- **内存**：缓冲内存占用需有上限，可配置。
- **落盘**：批量写 Parquet，避免逐条 IO；写入不阻塞行情回调线程。
- **启动时间**：从连接、查询合约全集到完成全部订阅，需在开盘前完成（目标控制在分钟级）。

### NFR-2 可靠性

- 断线重连、行情重订阅需自动恢复。
- 采集需具备幂等性：当日进程中断后重跑 `--once`，可与当日已落盘数据合并去重（合并写回同一合约文件）；历史日期无法从 CTP 回补，不在可靠性承诺范围。

### NFR-3 可观测性

- 记录每合约 tick 计数、订阅状态、连接状态、刷盘耗时等指标日志。
  tick 计数口径（v1.3 明确）：`logging.tick_mode: every`，每合约每累计到 `tick_interval`（默认 1000）的整数倍输出一次**累计值**；`first`（仅首次达标）变体**已删除**（配置校验会拒绝该值），原因见《整改方案.md》D16。

### NFR-4 可移植性

- 代码在 Linux 服务器与 macOS 本地电脑均可运行。
- CTP 依赖的 C++ 扩展需在目标环境可用（复用现有编译产物）。

### NFR-5 数据质量

- 落盘数据字段类型稳定、schema 固定，便于后续程序化读取。

## 5. 约束与假设

### 5.1 约束

1. CTP 行情订阅有数量限制（单次订阅约百级~千级合约，需分批），需实测确认；SimNow 对订阅数量另有额外限制，全市场规模压测需生产账号。
2. 期权合约数量随到期日动态变化，每日需重新查询。
3. 不同交易所 tick 推送频率不同（如股指期货高频 vs 部分商品低频），需统一缓冲策略。
4. 夜盘收盘时间因品种而异（23:00 / 01:00 / 02:30 三档），收盘触发需按分片内订阅品种的最晚时段配置。
5. 生产环境需实盘行情账号与权限；SimNow 用于开发验证。

### 5.2 假设

1. 用户已具备 CTP 行情账号（SimNow 或生产），配置方式沿用现有 `ctp_env_selector` 机制。
2. 本期"多机汇总"仅要求各自本地保存，不要求自动合并；跨机合并留待后续迭代。
3. 存储介质为本地磁盘（或挂载盘），单日单机数据量可被本地磁盘容纳。

## 6. 数据量估算（供容量规划）

> 以下为量级估算，需在实现阶段实测校准。估算基础：CTP 深度行情快照为 500ms 级推送（部分交易所单个 500ms 窗口推 2 条快照），活跃合约约 2 条/秒。

- **合约总数（2026-09-16 实测校准）**：全市场 **17386 个**（future 852 + option 15842 + spot_option 692），覆盖 SHFE 6764、GFEX 3820、DCE 3058、CZCE 2197、INE 827、CFFEX 720。原初估 3000~5000 明显偏低，容量规划与分片数量应以此为准。
- 单合约 tick 频率：活跃主力合约约每秒 2 条（实测 1.9 条/秒），冷门合约更少。
- 单日单合约 tick 量：约 4 小时交易时段 × 3600 秒 × 1 条 ≈ 1.5 万条（活跃主力可达数十万条）。
- 单条深度快照序列化后约 200~500 字节。
- **单日全市场数据量粗估**：万余合约 × 1.5 万条 × 300 字节 ≈ 数十 GB 至百 GB 量级（需分片到多机）。

> 结论：单机无法承载全市场，**分片是刚性需求**。
