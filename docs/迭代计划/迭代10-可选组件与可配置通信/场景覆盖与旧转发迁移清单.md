## 3 三个场所必须保留的差异

### 3.1 Binance

[当前 client](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/certlib/binance_client.py:59)按每 client 一套凭据执行同步 REST；EM01 可另建受限凭据 client。单个 runner 的成功不能证明一百进程共享配额和连接。新路径由账户 owner 接管订单与查询、Gateway 调度真实配额域，策略代理不能各自计算一整份账户/API key/IP 限额。

[M02](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/cases/M02/M02_strategy.py)和 [M03](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/cases/M03/M03_strategy.py)由案例自身调用 REST 创建/续期/删除 listen-key，尽管旧标签为 READ，仍是会话资源操作，未因此证明 WebSocket 断线或外部强退。[EM02](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/cases/EM02/EM02_strategy.py:31)使用本地暂停状态，[EM03](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/cases/EM03/EM03_strategy.py:44)涉及自行终止会话；操作引用字符串本身不证明外部后台动作发生。新控制路径需要请求、受理、上游观察和恢复各阶段的证据。

[EM01](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/cases/EM01/EM01_strategy.py:68)有真实账户管理写请求：签名 POST 将 `dualSidePosition` 设为 false；未提供可选受限凭据时使用主 client，成功后尝试恢复并读取 hedge mode。它不能归为无副作用权限校验。未来组件适配需独立 account_admin 授权及维护流程，核对所有策略的挂单/持仓前置条件、实际模式与恢复结果；UNKNOWN 不恢复普通写入。未支持此动作时保持能力缺失，不用本地拒绝冒充上游权限限制证明。

[T03](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/cases/T03/T03_strategy.py:1)是 resting LIMIT 挂单、受理后撤单并核实本次无残单，不是持仓清理。[TH01](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/cases/TH01/TH01_strategy.py:1)/TH03/TH05 只读本地阈值快照；runner 要求凭据配置，但 [connect](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/certlib/binance_client.py:180)仅访问公用 server time，不能描述为读取私有账户。TH02/04/06 虽有订单动作，告警仍由案例手动记录本地 Monitor 事件计算，不是新服务消费证明。

[certlib 工厂](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/certlib/__init__.py:43)仍有 Optional16/旧 gateway 分支，迁移时改成正常 SDK 组件后端，不据此保留或重启已退役的 Optional16。当前[本地监控对象](D:/source_code/backtrader/examples/live/000_live_certification/binance_penetration/certlib/monitor.py:23)也不能当作远程 Monitor 的生产接入证据。

### 3.2 OKX

[certlib 工厂](D:/source_code/backtrader/examples/live/000_live_certification/okx_penetration/certlib/__init__.py:17)明确拒绝非 direct 及未实现的组件组合，故“加配置即可使用新四包”目前不成立。P7 需要实际 SDK 适配，保留账户权限和案例动作语义。

[client](D:/source_code/backtrader/examples/live/000_live_certification/okx_penetration/certlib/okx_client.py:190)读取持仓模式，订单路径使用普通订单接口；部分案例固定 `posSide=long`，查询还带产品范围。新模型须校验实际 net/long-short、保证金模式和查询完整性，不能擅自切换账户模式，也不能把 SWAP 过滤结果当作全账户。原生条件单/算法单若未实现，明确拒绝，不以 LIMIT 路径冒充支持。

[M02](D:/source_code/backtrader/examples/live/000_live_certification/okx_penetration/cases/M02/M02_strategy.py)、[M03](D:/source_code/backtrader/examples/live/000_live_certification/okx_penetration/cases/M03/M03_strategy.py)包含错误 passphrase 与健康读取；[EM01](D:/source_code/backtrader/examples/live/000_live_certification/okx_penetration/cases/EM01/EM01_strategy.py)、[EM02](D:/source_code/backtrader/examples/live/000_live_certification/okx_penetration/cases/EM02/EM02_strategy.py)、[EM03](D:/source_code/backtrader/examples/live/000_live_certification/okx_penetration/cases/EM03/EM03_strategy.py)分别包含错误凭据/本地控制等替代演练。这些源码不能证明 WebSocket 断线恢复、外部权限修改或后台强退；本轮仅登记缺口。

其中 EM01 在坏 secret 的账户读取遭拒后，还会用正常 client 实际下限价单并撤单，不能只授予只读权限；它没有 Binance 的账户模式切换。TH01/TH03/TH05 策略只生成本地阈值快照，但 [LIVE runner](D:/source_code/backtrader/examples/live/000_live_certification/okx_penetration/certlib/runner.py:157)先 connect，包含签名账户配置 GET，和 Binance 的公用 time 请求不同。[T03](D:/source_code/backtrader/examples/live/000_live_certification/okx_penetration/cases/T03/T03_strategy.py:111)把 partially_filled 也当作可撤挂单；即使订单已取消，已成交部分仍可能留下头寸，不能宣称“账户已清理”。

### 3.3 SimNow / CTP

[certlib 工厂](D:/source_code/backtrader/examples/live/000_live_certification/simnow_penetration/certlib/__init__.py:20)同样限制 direct。当前 client 有交易日/代次、持仓今昨数量及显式开平标志，但 [OrderRef 生成与下单](D:/source_code/backtrader/examples/live/000_live_certification/simnow_penetration/certlib/ctp_client.py:454)仍依赖本地生成器。新 owner 需要持久引用分配和完整外部订单身份，防止多进程碰撞；交易日切换不能按机器自然日简单重置。

Gateway 的会话与查询调度应明确认证、登录、结算确认、行情/交易各自就绪及流控；Execution/Risk 处理投保、净/方向持仓、平今/平昨可平数量与预占，不能把统一 `close` 当作所有交易所通用。交易所元数据、合约到期和旧仓管理纳入 DIM06/DIM08；认证例单合约准入不自动扩展成任意多合约写权限。

[M02](D:/source_code/backtrader/examples/live/000_live_certification/simnow_penetration/cases/M02/M02_strategy.py:49)的断线观察依据包含“已尝试关闭”；新路径必须另外确认会话状态和资源结束。[EM01](D:/source_code/backtrader/examples/live/000_live_certification/simnow_penetration/cases/EM01/EM01_strategy.py:91)、[EM02](D:/source_code/backtrader/examples/live/000_live_certification/simnow_penetration/cases/EM02/EM02_strategy.py:120)包含本地停用/暂停；[EM03](D:/source_code/backtrader/examples/live/000_live_certification/simnow_penetration/cases/EM03/EM03_strategy.py:117)涉及登出、竞争登录或人工协助。venue_api 分支执行本会话 ReqUserLogout，属于上游自登出；竞争登录也不必然使原连接失效。operator-assist 才等待外部人员触发，后台权限/强退仍需真实外部控制接口及观察，组件不得模拟成功。

[T03](D:/source_code/backtrader/examples/live/000_live_certification/simnow_penetration/cases/T03/T03_strategy.py:1)与 Binance 一样是挂单—撤单—确认终态及无残单，不做持仓清理。TH01/TH03/TH05 策略本身只读本地阈值快照，但 SimNow [live runner](D:/source_code/backtrader/examples/live/000_live_certification/simnow_penetration/certlib/runner.py:184)会先登录账户；不能套用 Binance 只访问公用 server time 的连接语义。

## 5 多策略、多账户、多品种的功能归属

| 组件 | 优化后的核心职责 | 不应承担的职责 |
|---|---|---|
| `bt_api_gateway` | 系统共享行情、完整合约/订阅键、多周期/回补、账户会话与读模型、序列恢复、共享配额与公平调度；私有 worker 按账户隔离 | 不持有第二套订单权威，不计算策略信号，不把每个策略/品种变成一个 provider 连接 |
| `bt_api_risk` | 账户内共享资源池、策略预算、合约/底层集中度、可平量和组风险；并发原子预留与事实驱动释放 | 不把账户间资金相加后允许互用，不拿 Monitor 缓存做硬准入，不把缺失 Greeks 当零 |
| `bt_api_execution` | 每账户唯一订单入口、策略分账、ID/回报/恢复、净/双向/今昨仓语义；同包组协调处理两腿及受限同账户三腿 | 不向策略泄露 provider 凭据，不用独立 buy/sell 冒充组合恢复，不承诺原子成交 |
| `bt_api_monitor` | 系统、账户、策略、合约、组多维观察；有效阈值版本、事件去重、告警、授权控制及最终结果 | 不另开账户连接来重做同一份事实，不改变订单路由，不把告警送达当作风险拦截 |

100 个策略、10 个账户不产生 100 × 10 × 品种数套服务。建议 100 个 SDK 策略进程、10 个账户 owner（E/R 及本账户 G worker）、按行情源/权限分区的 G hub、系统 M，以及有组合交易时的 E 组协调角色。组协调可托管多个 portfolio；进程数与策略/合约数量不需要一一对应。通信由配置选择 `bt_api_transport_zmq`，领域合同不绑定 ZMQ，以便后续增加其他 transport。

无组件配置仍支持普通 direct/回测；只读观察可只选 G/M；受管单腿可不使用组协调；请求受管组合写入时，组/账户执行和必要风险事实是该功能的前提。组件可选不代表同一受管账户中的某个策略能绕过已启用政策直连下单。

## 6 旧转发退役与功能迁移

用户确定的目标：删除生产路径中的 `bt_api_py/forwarding` 与 `bt_api/bt_api_base/src/bt_api_base/gateway`。需要的行情和账户转发领域功能进入新的 `bt_api_gateway`；socket、连接认证和通用通信机制进入 `bt_api_transport_zmq`；中立端口/DTO 留 base，轻量代理/装配留 SDK。不能将整套旧服务换个 base 目录名继续保留，也不新增长期导入别名或双协议运行器。

### 6.1 功能去向

| 旧能力/耦合 | 目标位置 | 删除旧实现前的检查 |
|---|---|---|
| 行情订阅、去重、转发、客户端退出回收 | G 订阅服务及 SDK Store 代理 | GW01–03、DIM02；权限相容才合并上游 |
| 账户余额/持仓/订单事实读取、快照与增量 | G 账户 worker/读模型；订单归属由 E 提供 | scope/完整性、gap、快照接续和账户隔离 |
| 登录、私有连接、查询/重连配额 | G worker 与账户 owner 的 provider session 端口 | 一个账户一套必要会话集合；DIM06–07 |
| 原转发的命令派发与回报 | SDK 订单代理 → 唯一账户入口 → G/provider session | E 或合格的已有 OMS 负责订单状态/恢复；没有 writer 合同只能只读 |
| Socket、RPC、PUB/SUB、传输认证 | transport 实现；base 只声明端口/消息合同 | TRN01–03；新 G 不直接依赖 ZMQ 类型，transport 不依赖 provider SDK |
| provider 注册、通用模型/接口 | provider adapter + base 中立合同 | provider 插件不因 import 就加载可选 G 服务；普通 direct 零服务回归 |
| 旧远程配置与旧 wire | 离线迁移说明/转换器；新服务只运行新合同 | MIG02；不能等价转换则具体报错，不回退 direct、不运行旧监听器 |

### 6.3 切换顺序

1. P0 固定公共键、能力与动作合同，登记旧行为及消费方；不把旧类名直接当新架构。
2. P1–P6 实现新服务与 transport，完成所需能力；P7 切换 SDK/Backtrader/certlib 的正常入口并逐场景验证。普通 direct 和不安装组件路径同时保留。
3. P9B/P9C 完成 AFI 旧 Gateway 读写/启动消费方切换、P9D 清理对应旧依赖后，P7R 在版本边界移除旧目录、活动导出/配置执行分支和旧 wire，交付离线转换器及明确不兼容说明。按账户读写闭包切换，先关闭旧 owner 并核实状态，再启动新 owner；不为对比试验同时登录两套写会话。
4. 迁移未决订单、预留、归属和消费基线时保留原业务身份。UNKNOWN 未解决则保留处置责任，不能删库制造“全新就绪”。不能安全迁移的部署留在已记录旧版本，不能计作退役完成；回退也是完整版本的受控切换。
5. 子包每轮验收后先提交各自 dev，再提交父仓 gitlink；Backtrader 消费方按独立小轮提交。仅迁移已验证行为，不重复历史接受的 QA 来累积数量。

## 7 本轮和后续验收边界

当前产物为主计划、本清单和新增 AFI 接入规格。文档检查核对三份文件的链接、计划 ID、33 × 3 案例源码清单、9 个 unified 目录、配置示例及迁移表一致性。未运行策略、未连接账户、未执行订单或控制操作，也没有新正式案例 PASS。

后续按 P0–P8 小轮交付，先保证单账户单腿，再共享账户多策略，再同账户/跨账户两腿，接着受限三腿，最后非均匀百进程与双机。每个 venue 分别列出实际支持的产品、账户模式、合约类型、订单能力和证据层级。外部后台控制、原生算法单、期权实盘资格和 HFT 准入有缺口时明确标注，不用框架级验收代替。

AFI 分支按 P9A–P9D 的依赖并行推进，先共享读取和组合分析，再政策/交易控制与重复实现删除；不要求只读产品等待全部场所或三腿验收。新增 AFI01–AFI12 不替代原有服务、双机和 provider 证据。
